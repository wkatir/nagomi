# Nagomi store

Storefront and back office for Nagomi (なごみ), a B2C online store of computer peripherals and desk-setup accessories in El Salvador (keyboards, mice, desk mats, headphones, lighting and accessories, plus sets/combos), built for a university e-commerce course. Currency, time zone, country, thresholds and copy about the business come from the database. The store sells online: a server-side cart, a one-page checkout (guests allowed) with card (Wompi El Salvador), bank transfer or cash on delivery, order tracking at `/pedido/<code>`, coupons, reviews, a wishlist and back-in-stock requests.

Scaffolded with the official TanStack CLI (`@tanstack/cli create`, add-ons: drizzle, paraglide, shadcn, tanstack-query, form, better-auth; deployment: cloudflare; toolchain: biome). Generated files keep their CLI conventions.

Note: `tanstack add <add-on>` re-applies the whole template and overwrites project files. Back up first and keep only the add-on's new files.

## Domain rules

The schema is `src/db/schema/` (store, one module per area) and `src/db/auth-schema.ts` (generated by the Better Auth CLI). Integrity rules drizzle-kit cannot express are triggers and views in `drizzle/0001_integrity_triggers.sql` (tested in `src/db/migrations.test.ts` and `src/db/store-rules.test.ts`); each abort a request can hit is answered as a 409 by `src/server/domain/db-errors.ts` (wired in `onError`, `src/server/app.ts`). Pure rules live in `src/server/domain/*.ts`, each with tests.

### Money, time and records

- Money is integers in the minor unit of the currency from `store_settings` (cents for USD; the number of decimals comes from Intl, so JPY has none and KWD three: `src/lib/money.ts`). Lot costs are integer hundredths of a minor unit (`unit_cost_e4`, `allocated_shipping_e4`) so shipping can be spread over units; reports round to minor units (`e4ToMinor`). The currency cannot change once an order or purchase order exists (`409 currency_locked`).
- Instants are UTC strings. Calendar dates (ordered/received on, delivery estimate) and every "today", day boundary and dashboard day use `store_settings.time_zone`; day boundaries are DST-safe (`startOfLocalDay`). Dates in requests must exist (`isCalendarDate`).
- Every enum is a CHECK on its column. Adding a value later means rebuilding that table, so treat the lists as fixed (see the migration rules below).
- Business records are kept for 10 years and never deleted: no foreign key cascades on store tables, and triggers refuse DELETE on orders, order lines (except while the order is pending), payments, returns and their lines, purchase orders and their lines (except while it is a draft), receipts and their lines, lots, audit events, consents, page versions, price history, order status history, customers and customer addresses (an address is archived). Brands, categories, products, variants, product images, bundles and suppliers are archived, not deleted (triggers); a variant never moves to another product.
- Every admin write runs as one D1 `batch` (one transaction) together with its `audit_events` row (actor user id, action, entity type and numeric id, JSON data; codes and references go in the data). Actions are `<entity>.create`, `.update`, `.archive` or `.status` (with `from` and `to` in the data), e.g. `order.status`, `payment.create`, `return.create`, `inventory_movement.create`, `store_promise.status`; a payment's or return's event carries its `orderId`, so the order detail lists it (expression index `audit_events_order_idx`).
- Search ignores accents and case beyond ASCII (SQLite's `lower()` and `LIKE` fold ASCII only): searchable rows keep a `search_key` (NOT NULL) written by every API write path with `searchKey()` (`src/server/domain/search.ts`: NFD, combining marks removed, lowercase, single spaces; phones as their digits), and a term is normalized the same way before an escaped `LIKE` (`searchMatch`, `src/server/domain/search-sql.ts`). Keys: `orders` (code, the name given with the order), `customers` (name, email, phone digits), `brands` (name, slug), `product_translations` (name), `variants` (SKU, barcode), `suppliers` (name, contact name). The seed fills them. Admin searches match only the keys (products: name in the default locale, brand, SKU or barcode of any variant, or the slug), so `creme`, `CRÈME` and `Crème` find the same rows. Names and titles per language have no key: the lists of categories, bundles and collections match and sort them with `foldedText()` (`search-sql.ts`), which lowercases and replaces the Spanish accents (and `ñ`) in SQL, so "Ángel" sorts with the A's. Audit events, page versions and returns are never rewritten; a consent only gains its customer.

### Catalogue

- Admin API (every write in one batch with its audit event): `/api/admin/brands`, `/categories`, `/bundles`, `/products` (variants under `/products/:id/variants` and `/products/variants/:id`) and `/product-images`. The lists of brands, categories, bundles and collections are pages (see "Back office", "Lists") with a `status` filter, `q` and a sort whitelist; each also has `GET /options`, the whole set as `{ id, name, status }[]` for the selects of other screens. `GET /products/list` is the product-level page (filters `status`, `brandId`, `categoryId`, `q`; it gives `variantCount`); `GET /products` is unpaged and per variant, for the pickers. Nothing is deleted: `PATCH` with `status: "archived"`.
- Slugs are lowercase words joined by single hyphens, at most 80 characters (CHECK and API), unique per table (`409 duplicate_slug`). A product's slug changes only while it is a draft and a bundle's while it is not published (`409 slug_locked`).
- Categories: `sort_order` (>= 0, the default order of every list and of the storefront), `icon` (a lucide icon name from the fixed allow-list `keyboard`, `mouse`, `square`, `headphones`, `lightbulb`, `package`; CHECK and API, `CATEGORY_ICONS` in `src/lib/enums.ts`) and per locale a name, a `subtitle` (the home tile text, e.g. "Mecánicos y custom"), a description and SEO fields.
- `products.status`: `draft` (never shown), `published` (for sale), `archived`; a product is created as a draft. Publishing needs an active priced variant, the default locale's text and an active brand and category (API check and triggers, `publish_requires_price`). A brand or category used by a published product cannot be archived (`409 in_use`).
- Products also have `warranty_months` (integer >= 0, CHECK; the seed uses 12 for keyboards, mice, headphones and lighting and 6 for mats and accessories), `is_featured` (featured products sort first on the storefront and feed the home) and `badge` (`best_seller` or `new`, CHECK; labels are messages). Text per locale: name, tagline, `short_specs` (the card line, e.g. "75% · Switches Windy · RGB"), description and SEO title and description.
- Technical specifications are ordered label/value pairs per product: `product_specs` (position from 1, unique per product) with `product_spec_translations` (label and value, both non-blank, CHECK). `PUT /api/admin/products/:id/specs` replaces the whole list in one batch; every row needs the default locale (`409 spec_requires_default_translation`). The product page shows them in order.
- Variants: SKU in the format `AAA-000` (three capitals, a dash, three digits: CHECK `variants_sku_format`, `SKU_REGEX`; the API upper-cases input), unique (`409 duplicate_sku`); price, compare-at price (above the price), an optional `option_label` (colour, switch type...; replaces sizes), barcode (stored as GTIN-14) and reorder point. Every variant write sets `variants.updated_by` to the acting admin, which the price history records. A variant with units on hand is archived only with `archiveWithStock: true`.
- The admin product list gives per variant `onHand`, `committed`, `available` and `latestUnitCost` (the landed unit cost of the latest lot bought at a price; null for support, see "Accounts and roles"). `GET /api/admin/products/:id` also gives `publishMissing`, the specs and, per variant, `skuEditable` and `onHand`.
- Catalogue text lives in `*_translations` tables with fallback to the default locale; creating a new category, bundle or product needs the default locale's text. Store name, legal identity, legal pages and all copy live in the database; the code holds no business data.
- Brands have page text per locale (`brand_translations`: description, SEO title and description).

### Sets / Combos (bundles)

- `bundles` (slug, status `draft`/`published`/`archived`, featured flag, position, `price` in minor units > 0) with `bundle_translations` (name, description, SEO) and `bundle_items` (variant, `quantity` >= 1, position; one row per variant, so items are distinct). Archived, never deleted (trigger).
- Rule: a published bundle has at least two items, every item is an active priced variant of a published product, and its price is below the sum of quantity x current price of its items. Triggers enforce it when a bundle is published or its price changes (`bundles_published_two_items`, `_items_available`, `_price_below_items`), when items of a published bundle are inserted, updated or deleted (`bundle_items_published_*`), when a variant's price or status changes (`variants_bundle_price_below_items`, `variants_bundle_item_available`: a price change that would make a published bundle cost as much as its items is refused) and when a product leaves `published` (`products_bundle_item_available`). A bundle cannot be inserted as published. Drafts are checked by the API on save (`bundleRefusal`, `src/server/domain/bundles.ts`): 409 `bundle_requires_two_items`, `bundle_item_unavailable` (with `variantIds`) or `bundle_price_not_below_items` (with `price`, `itemsTotal`).
- Admin API `/api/admin/bundles`: `GET /` (page; sorts name, position, items, price, featured, status), `GET /options`, `GET /:id` (texts, items with SKU, price and status, `itemsTotal`, `saving`), `POST /`, `PATCH /:id`, `PUT /:id/translations/:locale`, `PUT /:id/items`.

### Price history

- `price_history` (variant, old price, new price, `changed_at`, `changed_by`) is written by triggers, never by the API: one row when a variant is inserted with a price and one each time its price changes, with `variants.updated_by` as the actor. Append-only (UPDATE and DELETE refused, `price_history_append_only`). `GET /api/admin/products/:id/price-history` lists it newest first with the actor's name.

### Collections

- `collections` (+ `collection_translations`: title, description, cover alt text, SEO title and description; `collection_products` with a position from 1, unique per collection): curated groups of products such as "Más vendidos", with the product lifecycle (`draft`, `published`, `archived`; created as a draft), a position, a `show_on_home` flag and an optional cover (a media file). Publishing needs the default locale's text and at least one product (`409 collection_requires_products`, checked again inside the write); the slug changes only while not published (`409 slug_locked`). A collection holds products that are not archived (API and trigger, `409 reference_unavailable`); the storefront shows only its published products, in the collection's order. Archived, never deleted (trigger).
- Admin API: `GET /api/admin/collections` (a page: `status`, `q`, sorts `title`, `position`, `products`, `home`, `status`), `GET /options`, `GET /:id`, `POST /` (slug, position, showOnHome, coverMediaId, translations with the default locale, optional productIds), `PATCH /:id` (slug, position, showOnHome, coverMediaId, status), `PUT /:id/translations/:locale` (replaces the text), `PUT /:id/products` (`productIds` in order; replaces them), `PUT /order` (`collectionIds`: every collection that is not archived, first to last; `409 collections_changed` otherwise). Audit: `collection.create`, `.update`, `.status`, `.archive`.

### Home slides

- `home_slides` (+ `home_slide_translations`: title, body, CTA label, image alt text): the home hero's slides (the storefront uses the first one as its hero), with the product lifecycle, a position, a desktop image and an optional mobile image (media files), a link and optional start and end dates (local days of the store, both included). The storefront shows published slides within their dates, by position. The link is a storefront path without the locale prefix (`/products?category=teclados`; the storefront adds `/en`), checked by `isStorePath` (`src/server/domain/store-path.ts`: one leading `/`, printable ASCII without spaces or backslashes, at most 300 characters, not `/api`, `/admin`, `/media` or a locale prefix) and by a CHECK. Publishing needs the default locale's text. Archived, never deleted.
- Admin API: `GET /api/admin/home-slides[?status]` (all of them, not paged: the list is short), `GET /:id`, `POST /` (desktopMediaId, mobileMediaId, linkPath, startsOn, endsOn, position, translations with the default locale), `PATCH /:id` (those fields and status), `PUT /:id/translations` (`translations` by language; each language given is replaced as a whole, title and imageAlt required, in one batch, and the others are left as they are; it replaced the per-locale PUT), `PUT /order` (`slideIds`: every slide that is not archived). Audit: `home_slide.*`.

### Storefront catalogue

- The store page (`GET /api/products`) reads the whole published catalogue in one D1 batch and refines it in memory (`src/server/domain/storefront-catalog.ts` loads it; `catalog-query.ts` is the pure filtering, faceting, sorting and paging, with tests), which stays cheap for a catalogue of hundreds of products. A product shows its cheapest active priced variant (price, compare-at price, option label and SKU on the card), its short spec line, badge and featured flag, and the number of variants.
- Search (`q`) ignores accents and case: every word must appear in the product's brand, name (the page's locale and the default one), category, short specs or SKUs. Refinements: `category`, `brand`, `collection` (repeat a parameter for several values; values of one refinement are alternatives, refinements narrow each other), `minPrice`/`maxPrice` (minor units, both included, on the card's price) and `availability`.
- Availability follows the stock: a variant is `in_stock` while it has sellable units (see Orders, "Stock"), else `sold_out` and it cannot be ordered ("Agotado"). Each variant carries `maxQuantity`, its sellable units up to `max_quantity_per_line`, so the exact stock above that limit is not published. A card shows the cheapest variant in stock, else the cheapest; a product is `in_stock` when any variant is.
- Facets: each value counts the products matching every other refinement but not its own facet's (standard faceting); a facet lists the values found among the products matching the search, plus the selected ones; `priceRange` is that of the products matching everything but the price.
- Sorts: `featured` (in stock first, then featured products, then category `sort_order`, then name; with one collection chosen, the collection's order), `newest` (creation, newest first), `price_asc`, `price_desc`, `name` (in the page's locale).
- Related products (`src/server/domain/related.ts`): at most 8, never the product itself; a product in the same published bundle weighs most, then the same category, then the same brand; at most two per category while others are left; each marked `alternative` (same category) or `complement`.

### Media

- Images (product photos, home slides, collection covers, editorial photos) live in the R2 bucket bound as `MEDIA` (`wrangler.jsonc`) under a content-addressed key, `<sha256>.<ext>`, and are served by the Worker at `GET /media/<key>` with the stored type, `Cache-Control: public, max-age=31536000, immutable` and the hash as a strong `ETag` (a matching `If-None-Match`, compared weakly, is answered 304 without reading R2; `*` answers 304 when the object exists). Anything that is not such a key is a 404 (`src/server/media.ts`).
- Upload: `POST /api/admin/product-images`, multipart with `file`, `productId`, `kind` (`packshot`, `lifestyle`, `detail`), optional `variantId` (the photo then shows only for that variant; a trigger keeps it a variant of the same product) and alt text as `alt.<locale>`, the default locale required. JPEG, PNG, WebP or AVIF up to 5 MB and 10,000 px on a side (`415 unsupported_image_type`, `413 image_too_large`); the type and pixel size are read from the file itself, and a file that is not what it declares or is incomplete (a PNG without IDAT and IEND, a JPEG without its scan, a WebP or AVIF whose boxes do not fit) is `400 invalid_image` (`src/server/domain/images.ts`; JPEG EXIF rotation swaps width and height). The same photo twice on a product is `409 duplicate_image`. A body that is not a multipart form is `400 invalid_form` (also for `POST /api/admin/media`). Resize photos before uploading (about 1600 px); there is no server-side resizing.
- `PATCH /api/admin/product-images/:id` changes kind, variant, status (archive) and alt texts (the default locale's cannot be removed); `PUT /api/admin/product-images/order` sets the order of all the product's active photos. A photo's file and product never change (trigger). Archived photos stay in R2: a key is never reused for other content.
- The storefront returns each photo's URL, kind, width, height and alt text in the page's locale, else the default locale's, else the brand and product name (an accessibility fallback for data that slipped past the checks, never an error), and renders them with `width` and `height`. Publishing a product, and restoring an archived photo, need alt text in the default locale on every active photo (`409 image_alt_required`); changing the default locale is refused while a published product's photo has no alt text in it.
- Every image file is a `media_files` row (content key, type, size in bytes, pixel size; a row never changes and is never deleted, and its key is a content key, CHECK). A product photo (`product_images`) points at its file with `media_file_id` and adds the product, variant, kind, order, status and alt texts, so one file can be a photo of several products; uploading a product photo registers its file when it is new. Home slides and collection covers reference a file by id, uploaded with `POST /api/admin/media` (multipart `file`; the same file again answers its existing row with 200); `GET /api/admin/media` (newest first, `cursor`/`limit`, answers `{ items, nextCursor }`), `GET /api/admin/media/:id`, `GET /api/admin/media/:id/usage` (where the file is shown: the home slides that use it as wide or phone picture, the collections it covers and the product photos made from it, archived ones included; names in the store's default language, null without text in it). Audit: `media_file.create` (a product photo's `product_image.create` carries its file's key and size).
- Seed photos are in `seed/images` (`<lower-case SKU>.webp`, one packshot per product); `bun run media:seed` uploads them to the local bucket (`bun seed/media.ts --remote` for production) and registers each with its alt text, the product name in each locale. Editorial images are in `seed/editorial` with `manifest.json` (file, alt text per locale, credit, license): `hero.webp` (home slide 1, links to `/products`), `combo-banner.webp` (home slide 2, links to `/sets`) and `sidebar-torii.webp` (registered as a media file only, for the storefront redesign). `seed/home.json` (slides) and `seed/collections.json` point at them by file name; the build fails when a file, an alt text or a referenced product is missing. `media:seed` only inserts what is missing, so it can run again.
- Each `/media` request is a Worker request (static assets are not), counted in the plan's request limits. If that becomes a cost, serve the bucket on its own custom domain (for example `media.<store domain>`) and change `mediaUrl`.

### Stock

- Stock is never stored: it is the sum of `inventory_movements` per lot. The ledger is append-only (corrections are new movements) and a trigger refuses any movement that would take a lot below zero (`lot_balance_negative`, answered as 409 `stock_changed`; the whole batch rolls back, so a stale read can never oversell).
- Movement kinds: `receive`, `return` and `cancellation` (positive), `sale` and `waste` (negative), `adjustment` (either sign; a stock count is an adjustment with the reason `count_difference`). A sale points at its order line (only while the order is pending, never more units than the line, only from a lot of the line's variant); a cancellation puts a cancelled order's units back in the lot they left (never more than left it); a return, and the waste of a written-off return, point at the return line. `waste` and `adjustment` need a reason (`damaged`, `demo_unit`, `own_use`, `lost_theft`, `count_difference`, `customer_return`, `other`; `other` needs a note).
- Lots carry their code, receipt line and landed unit cost; peripherals do not expire, so lots exist for landed cost and the ledger only.
- Orders take their units FIFO when they are placed: the oldest lot first, by lot id, across every line of the same size (`allocateLines`, `src/server/domain/cart-pricing.ts`).
- Low stock: a variant is low when its units on hand are at or below its own `reorder_point`, or `store_settings.low_stock_threshold` (5 in the seed) when it has none. Stock lists, the dashboard and the stock report flag it as `lowStock`.

### Purchasing

- Suppliers (`/api/admin/suppliers`): name unique ignoring case (`409 duplicate_name`, checked again inside the write), contact name, phone (stored in E.164, read in the store's country), email (trimmed and lowercased), payment terms and notes as text, and `lead_time_days` (days from placing an order to having the units; null until the supplier states it, never below 0); archived, never deleted. New purchase orders, and placing a draft, need an active supplier (`409 supplier_archived`, API and triggers); an archived supplier's open orders can still be received or cancelled. Blank notes on purchase orders and receipts are stored as null (CHECK on purchase orders). `GET /api/admin/suppliers` is a page (sorts `name`, `leadTimeDays`, `openPurchaseOrders`, `createdAt`; `status`; `q` = name or contact), `GET /options` is the whole set as `{ id, name, leadTimeDays, status }[]` (`?status=` narrows it; a purchase order lists archived ones too) and `GET /:id` adds `openOrders`, the supplier's purchase orders that are draft, ordered or partially received.
- Supplier items (`supplier_items`): what a supplier sells of a variant, one row per supplier and variant (`409 duplicate_supplier_item`), with the supplier's code, `pack_size` (orders are whole packs) and `min_order_quantity`, each null while not known; archived, never deleted, and the supplier and variant never change (triggers); only created for an active supplier. At most one active item per variant is preferred (partial unique index); marking one preferred moves the flag in the same batch; asking for an archived item, or one of an archived supplier, to be preferred is `409 supplier_item_archived` or `409 supplier_archived`, and archiving the preferred item drops the flag. API: `GET /api/admin/suppliers/items?variantId&supplierId&status`, `POST /api/admin/suppliers/:id/items`, `PATCH /api/admin/suppliers/:id/items/:itemId` (code, pack, minimum, preferred, status), audited. The seed links the supplier to the variants of its purchase order with no lead time, pack or minimum.
- Purchase order: `draft -> ordered -> partially_received -> received`; `draft`, `ordered` and `partially_received` can be cancelled (for a partial one: the rest will not come). A reference is unique among the supplier's purchase orders that are not cancelled, so a cancelled draft frees it. Several lines may share a variant (e.g. free units at cost 0). A draft can be corrected (`PATCH /api/admin/purchase-orders/:id`: reference, notes, tax treatment, lines and costs); lines are fixed once receiving starts and never drop below what arrived. The status always matches the receipts (trigger `purchase_order_status_mismatch`). Purchase orders are mounted at `/api/admin/purchase-orders`: `GET /` is a page (sorts `createdAt`, `reference`, `supplier`, `status`, `total`, `orderedOn`; filters `status`, `supplierId`, `from`/`to` local days of creation; `q` = reference or supplier), `GET /:id` is the order with its lines, what arrived of each and every delivery with the lots it created, `POST /` creates an order (a draft, or ordered when `orderedOn` is given), `POST /from-reorder` (`supplierId`, `variantIds` and the reorder parameters) creates a draft for one supplier from the reorder suggestions (`409 nothing_to_order` when none applies; a variant never bought starts at cost 0, to be filled in; the reference is the day's date, with `-2`, `-3` when the supplier already has one that day) and answers `{ id, reference }`, and `POST /:id/order`, `/:id/cancel` and `/:id/receive` move it along.
- A receipt is one delivery (`received_on`, supplier invoice reference, shipping cost, required even when 0). It cannot be dated after the store's today or before the order date. Each receipt line creates exactly one lot and its single `receive` movement of the same quantity. Receipts go only into `ordered` or `partially_received` orders and never beyond the units still expected (trigger `receipt_exceeds_ordered`); the order status is recomputed from what arrived. A receipt's order, date and shipping cost cannot change afterwards.
- Landed cost: the receipt's shipping is spread over its lines by line value (units x supplier unit cost; by units when every line is free) with the largest-remainder method, so the shares add up exactly. A lot's unit cost is (supplier cost x units + its share) / units, rounded half up to a hundredth of a minor unit (at most half a hundredth of a cent per unit off the invoice). Lot costs cannot change after the fact. Whether supplier prices include IVA is recorded per purchase order (`tax_included`); IVA paid while not IVA-registered is part of cost.

### Orders

- Status machine (`src/server/domain/order-state.ts`, the same table in trigger `orders_status_transition`): `pending` (stock reserved, awaiting payment) → `paid` (payment confirmed) → `shipped` (courier and tracking recorded) → `delivered` (final). A cash-on-delivery order goes `pending` → `shipped`, and is `delivered` only once its cash is recorded. `cancelled` only from `pending` or `paid`. Triggers also require: `paid` and `delivered` with confirmed payments (net of refunds) of at least the total (`order_not_paid`), `shipped` with `shipped_at` and a courier, every line's units taken from stock before leaving `pending` (`order_units_not_taken`), a code redeemed before leaving `pending`, and nothing about a delivered or cancelled order changes afterwards (`order_is_final`).
- An order is placed with every term fixed (`POST /api/checkout`): customer name, email and phone (`+503` and 8 digits), structured delivery address (department, municipality, address line, reference), zone and its name, shipping method and fee, payment method, prices, discount and code, the IVA included (`tax_included`, at `store_settings.tax_rate_bp`), the delivery estimate (the zone's days from the store's today) and the summary shown (`confirmation_message`, `src/server/domain/confirmation.ts`). None of these change afterwards (trigger `order_terms_locked`); the code, idempotency key, request hash, locale, channel, email, phone and creation time never do (`order_identity_locked`). `paid_at`, `shipped_at`, `delivered_at` and `cancelled_at` are written once, by the status change they belong to. `total = subtotal - discount + shipping` is a CHECK.
- Order lines snapshot the SKU, brand, product name, option label and unit price. A set (bundle) is one `order_bundles` row at the set's price, and its items are order lines pointing at it, each with a share of the set's price in proportion to its list price (`allocateBundle`, `src/server/domain/cart-pricing.ts`), so the lines add up to the subtotal and a returned item refunds a fair share. Lines are never changed or deleted.
- Stock policy: the units leave the lots when the order is placed. The order, its lines, one `sale` movement per line and lot (first in, first out across every line of the same size, `allocateLines`), the coupon's redemption, the consents and the emptied cart are one D1 batch: a lot can never go below zero (trigger `lot_balance_negative`), so when another order took the last units the whole batch rolls back and the customer gets `409 insufficient_stock` with what is left. Cancelling a pending or paid order puts every unit back in the lot it left (trigger `orders_cancel_returns_stock` writes `cancellation` movements dated by the cancellation) and releases the coupon (`orders_cancel_releases_coupon`). What is on hand is what can be sold: there are no "held" units.
- Unpaid card and transfer orders are cancelled after the payment deadline (`store_settings.followup_pending_payment_hours`, 48 h in the seed): there is no cron, so `POST /api/admin/orders/expire-pending` (the button on the follow-up screen) cancels every order the follow-up view lists as `collect_payment` and still without a payment; running it again changes nothing. Cash-on-delivery orders are never cancelled this way.
- Follow-up (`order_followups` view, deadlines in settings): `collect_payment` for pending card/transfer orders (48 h), `ship` for paid and pending cash-on-delivery orders (24 h), `confirm_delivery` for shipped orders (96 h); a row appears once its deadline has passed.
- Order status history: triggers write one `order_status_history` row (from, to, `changed_at` = the order's own timestamp of that step) when an order is inserted and at each status change; append-only.
- Checkout requires acknowledging the privacy notice and the terms and offers optional marketing by email and WhatsApp. The order stores four `customer_consents` rows (granted or not), each pointing at the exact page version shown (trigger `customer_consents_page_matches_purpose`), with the order's customer.
- Checkout is closed (`503 checkout_not_configured`, `store.checkoutOpen = false`) until the legal identity (legal name, tax ID label, tax ID, address) and published `privacy` and `terms` pages exist; pricing needs `tax_rate_bp` (`503 store_not_configured` otherwise).
- `delivered_at` starts the return window (`store_settings.return_window_days`).

### Cart and checkout

- `carts` (random 32-hex id in the httpOnly cookie `nagomi_cart`, 60 days; nullable `customer_id`, one cart per customer; the coupon code as typed) and `cart_items` (one size or one set per line, unique per cart, quantity > 0; a size must be published and priced, a set published: triggers). No prices are stored: every read prices the cart from the catalogue (`priceCart`, `src/server/domain/cart.ts`).
- A guest cart becomes the customer's on the first cart request after sign-in: merged into the customer's own cart (quantities summed, each capped at what is left and at `max_quantity_per_line`) or claimed. A signed-out browser never sees a customer's cart.
- Totals: subtotal, the coupon's discount, shipping from the delivery municipality (the zone's fee, free from `free_shipping_from` on subtotal minus discount), total, and the IVA included in it (`includedTax`: total × rate / (1 + rate), rounded half up, rate `tax_rate_bp` = 1300). Without a municipality the total leaves shipping out and says so.
- Payment options come with why one is unavailable: `card` needs the Wompi keys, `bank_transfer` the bank details in settings, `cash_on_delivery` an address in its zone (`store_payment_methods.shipping_zone_id`, metro) and a total up to its `max_total` (US$150): reasons `not_configured`, `outside_zone`, `address_required`, `over_max_total`.
- Checkout (`/checkout`, one page, guest allowed): name, email, phone (shown with `+503`, numeric keyboard), a saved address (signed in) or department, municipality (El Salvador list), address line and reference, payment method, coupon, terms, privacy and marketing. The API validates every field and answers `422 invalid_fields` with a code per field (`required`, `invalid`, `unknown`, `no_shipping_zone`, the payment reason), `409 cart_changed` with the priced cart when a line is no longer available or beyond stock, `409 promotion_invalid` with the reason, and is rate limited (`ORDER_LIMITER`). A retry with the same idempotency key returns the same order.
- Confirmation and tracking: `/pedido/<code>` (`?nuevo=1` after checkout, `?pago=tarjeta` back from Wompi) reads the order from the API, never from the query string: code, status, totals with IVA, the bank details and reference for a transfer, the cash note for cash on delivery, the payment button for a card order, address, estimate, courier and tracking, and the status timeline. The browser that placed it opens it through a signed cookie (`nagomi_orders`, the last 5 codes); another browser needs the order's email (rate limited); a signed-in customer opens their own.

### Card payments (Wompi El Salvador)

- Docs: https://docs.wompi.sv (authentication, `metodos-api/enlace-de-pago`, `redirect-url`, `webhook/definicion-webhook`, `webhook/validar-webhook`, `metodos-api/transaccion_prueba`) and the API description at https://api.wompi.sv/swagger/v1/swagger.json.
- `src/server/payments/wompi.ts`: an OAuth2 client-credentials token from `https://id.wompi.sv/connect/token` (`audience=wompi_api`, cached until a minute before it expires), then `POST https://api.wompi.sv/EnlacePago` with our order code as `identificadorEnlaceComercio`, the total in dollars, card only, `urlRedirect` = `/pedido/<code>?pago=tarjeta`, `urlWebhook` = `/api/payments/wompi/webhook`, non-editable amount and one successful payment. The order keeps the link (`payment_url`) and a pending `payments` row (`wompi-link:<id>`); `POST /api/orders/:code/pay` makes a new link for a pending card order.
- Webhook (`POST /api/payments/wompi/webhook`): the `wompi_hash` header must be the HMAC-SHA256 (lower-case hex) of the raw body with the API secret (`401 invalid_signature`). A transaction id already recorded changes nothing; a declined result records nothing; the order must be a card order with exactly the same total (`409 amount_mismatch`). The payment row becomes confirmed with the transaction id (unique) and the order `paid` in the same batch. The redirect never changes anything.
- Secrets `WOMPI_CLIENT_ID` (the business's App ID) and `WOMPI_CLIENT_SECRET` (API Secret), both or neither (`.dev.vars.example`). They are optional, so they are not in wrangler.jsonc's `secrets.required` (its schema has no optional list); without them the card option is listed as unavailable and checkout refuses it. Test mode is the business's development mode in the Wompi panel (every card approved except CVV 111); no Wompi account was created for this project.

### Promotions (coupons)

- `promotions` (+ `promotion_translations`): a code (stored in capitals, 3 to 32 letters, digits, `-` or `_`; typed in any case), `percentage` (1 to 50) or `fixed` (minor units), an optional minimum subtotal, optional dates (local days, the start before the end: CHECK), an optional total limit, `per_customer_limit` 1 (once per customer email) or none, `first_order_only` (only for an email without an earlier order that was not cancelled), status `active`, `inactive` or `archived`.
- The discount (`src/server/domain/promotions.ts`): a percentage of the subtotal rounded half up, or the fixed amount up to the subtotal, nothing below the minimum; the same formula is trigger `orders_promotion_discount_insert`, and an order without a code has no discount.
- Uses are `promotion_redemptions` rows (one per order, the order's email; `customer_key` = the email when once per customer) not released. Triggers check, when the order is written: the code is active, under its total limit, for a first order when it says so, and the row matches its pending order; the partial unique index (`promotion_id`, `customer_key`) refuses a second use of the same email (`409 promotion_limit_reached`). A cancelled order releases its row. Dates are checked by the API (the database has no time zone). The cart evaluates the code with the signed-in customer's email or, for a guest, leaves the per-email rules to checkout (`emailCheckPending`).
- Once a code was used, its code, type, value, minimum, per-customer limit and first-order flag never change (`409 promotion_in_use`; trigger).
- Admin API: `GET /api/admin/promotions` (sorts `createdAt`, `code`, `usage`, `startsOn`, `endsOn`; `status`; `q`) with `usage` and `termsLocked`, `GET /:id` (latest 50 orders), `POST /`, `PATCH /:id`, `PUT /:id/translations/:locale`.

### Payments and returns

- `payments` rows are money in (`payment`) or out (`refund`), positive, status `pending`, `confirmed` or `failed`, with method, reference, provider transaction id (unique), recorder and time; final once out of `pending`. Refunds never exceed confirmed payments, and a refund for a return belongs to the same order (triggers).
- What an order owes is derived (`amountOwed`, `src/server/domain/payments.ts`): nothing when cancelled; otherwise the kept units at their price, minus the discount in proportion, plus shipping while a unit is kept. The payment status (`unpaid`, `partially_paid`, `paid`, `refund_due`, `refunded`, `nothing_due`) is derived, never stored. A paid order that is cancelled is `refund_due` until the refund is recorded (`POST /api/admin/orders/:id/refunds`).
- `POST /api/admin/orders/:id/mark-paid` (optional `reference`) records the balance with the order's method — a transfer seen in the bank, or the cash a courier collected — and a pending order becomes `paid` in the same batch.
- Returns (`returns`, `return_lines`: `restock` or `write_off`) are for shipped or delivered orders, never more than left that lot for that line (triggers); the order keeps its status.

### Reviews, wishlist and back-in-stock alerts

- `product_reviews` (product, customer, rating 1–5 CHECK, title, body, status `pending`/`approved`/`rejected`, timestamps; UNIQUE customer + product). Trigger `product_reviews_requires_delivered_order`: only a customer with a delivered order containing the product can review it; the author and product never change. Writing or editing one sends it to moderation. Catalogue cards and the product page carry `rating` (`average` to one decimal over approved reviews, `count`).
- `wishlist_items` (customer + product PK). `stock_alerts` (variant, email lower-case, `created_at`, `notified_at`; one pending per email and size): requested from a sold-out product page; the store sends no email, staff copy the addresses in `/admin/stock-alerts` and mark each one notified.

### Shipping

- `shipping_zones` (+ translations): method, fee, delivery days, position, active or archived, and `covers_rest`. A zone lists the municipalities it serves in `shipping_zone_municipalities` (primary key the municipality, so one zone per municipality, `409 municipality_in_other_zone`; CHECK against the 44 municipalities); the one active zone with `covers_rest` (partial unique index) serves every other municipality and lists none (triggers, `409 zone_covers_rest`). `zoneForMunicipality` and `zoneFee` (`src/server/domain/shipping.ts`) resolve a municipality to its zone and fee.
- Free shipping is a setting, `store_settings.free_shipping_from` (subtotal after discount; US$50 in the seed), not per zone. Seed: `metro` (own delivery, US$3.50, 1–2 days: San Salvador Centro, Norte, Sur, Este and Oeste, La Libertad Sur and La Libertad Este, i.e. Santa Tecla and Antiguo Cuscatlán) and `national` (courier, US$5.00, 2–4 business days, covers the rest).
- Admin API: `GET /api/admin/shipping-zones` (page), `GET /options` (active zones with fee, days, slug, `coversRest` and municipalities), `GET /:id`, `POST`, `PATCH /:id`, `PUT /:id/translations/:locale`. Confirmed orders keep the fee and name they were given.

### Settings and promises

- Store rules are `store_settings` columns, edited in `/admin/settings`: `time_zone`, `country_code`, `tax_id_label`, `order_code_prefix`, `max_quantity_per_line`, `return_window_days`, `free_shipping_from`, `low_stock_threshold`, the customer segment thresholds `frequent_customer_min_orders` (>= 2) and `inactive_customer_days`, the follow-up deadlines in hours `followup_pending_payment_hours`, `followup_paid_unshipped_hours` and `followup_shipped_undelivered_hours`, and the social links `discord_url`, `instagram_url`, `tiktok_url`, `youtube_url` (https only, CHECK). Values live in the seed (3 orders, 90 days, 48/24/96 hours), never in code; the API answers `503 store_not_configured` while a required setting is empty.
- Payment methods are rows of `store_payment_methods` (`card`, `bank_transfer`, `cash_on_delivery` in the seed) with a `position`, an optional `max_total` and an optional `shipping_zone_id`: cash on delivery is limited to US$150 and the metro zone. The settings API reads and writes them as `paymentOptions` (array order is the position).
- Legal identity (legal name, NIT, address) and the contact email are labelled placeholders in the seed (`[Razón social pendiente]`, `[NIT pendiente]`, `[Dirección pendiente]`, `hola@nagomi.example`) that the admin replaces; the social URLs are placeholders too.
- Pages (`about`, `terms`, `privacy`, `shipping`, `returns-warranty`, `contact`, `faq`) are seeded in both locales: the privacy notice under El Salvador's Ley para la Protección de Datos Personales, the terms with the 8-day retracto from delivery of the Ley de Protección al Consumidor and the product warranty, the shipping policy with the zones above. `pages.footer_position` (unique, > 0) puts a page in the footer, in order: about, terms, shipping, contact. There is no admin editor for it yet.
- Prices and dates use the Intl locale `<language>-<country_code>`. Blank text settings are stored as null. Changing `default_locale` is refused (`409 default_locale_untranslated`) while a published product, promise, page or bundle, an active shipping zone or an active category has no text in the new locale.
- Store promises (`store_promises` + translations: `warranty`, `fast-shipping`, `returns`, `secure-payment`, `pay-on-delivery`) hold facts only and are published when true. Text may say `{return_window_days}`; such a promise cannot be published, nor the window cleared, while the setting is empty.
- Admin API (`/api/admin/settings`): `GET /` and `PATCH /` (the rules above and `paymentOptions`), `GET /promises`, `PATCH /promises/:id`, `PUT /promises/:id/translations/:locale`, `GET /pages`, `GET /pages/:id/versions?locale` and `PUT /pages/:id/translations/:locale` (saves the next version).

### Accounts and customers

- Roles are stored on the Better Auth user (`users.role`, admin plugin with `defaultRole: "customer"`): `customer`, `support` (atención al cliente) and `admin`; a trigger refuses any other value. Emails are trimmed and lower-cased before Better Auth sees them (a request hook in `src/lib/auth.ts` and a `databaseHooks` hook) and a trigger refuses an unnormalized one.
- Customers sign up and sign in with email and password at `/api/auth/sign-up/email` and `/api/auth/sign-in/email` (passwords 10 to 128 characters; sign-up limited to 3 per minute per IP, sign-in to 5). A new customer account creates its `customers` row, or links the guest customer that already has that email (`linkCustomerAccount`, `src/server/domain/customer-accounts.ts`); staff accounts get none. A role cannot be chosen at sign-up.
- Staff accounts are created with `bun run admin:create -- --email x@example.com --name "Name" [--role admin|support]` (default `admin`; password from `ADMIN_PASSWORD` or generated and printed once).
- `customers.auth_user_id` (nullable for guests, unique, FK to `users`) is set once, only to a `customer` account (triggers `customers_account_is_customer_insert`, `customers_account_locked`). The email is the identity: unique when present (partial unique index) and stored normalized (CHECK); the phone is optional and must be El Salvador's `+503` and 8 digits (CHECK; the API answers `422 phone_not_salvadoran`). Customers are never deleted.
- `customer_addresses`: recipient name, department, municipality, address line (colonia, street), reference point, phone (`+503`, CHECK), `is_default` (at most one per customer, partial unique index; only on an active address) and status. The department and municipality must be one of El Salvador's 14 departments and its municipalities (the 44 of the 2024 reform, `src/lib/sv-locations.json`); the API validates them with `isSvMunicipality` and a CHECK lists every valid pair. Addresses are archived, never deleted (trigger), and never move to another customer.
- Segments are the view `customer_segments` (`drizzle/0001`): from the customer's bought orders (paid, shipped, delivered) and the settings, `new` (none), `inactive` (last one older than `inactive_customer_days`), `frequent` (at least `frequent_customer_min_orders`) or `occasional`; null while a threshold is empty. Labels: Nuevo, Ocasional, Frecuente, Inactivo.
- Follow-up is the view `order_followups` (see Orders): orders past their deadline with their `action`, `due_at` and `hours_overdue`.

- Search: `GET /api/admin/search?q=` answers the groups `orders`, `products`, `customers`, `suppliers`, `purchases`, `brands`, `categories`, `bundles`, `collections` and `promotions`, each `{ id, label, hint }[]` with at most 5 hits (the groups support cannot read are empty). Orders and products query their own searchable columns; the other groups call the list function of their module, so a record is found by what its screen would find it by.
- Inventory (`/api/admin/inventory`): `GET /` is a page of the stock per variant (`view` = `low` or `out`; `q` = product, brand, SKU or barcode; rows with `optionLabel` and `lowStock`). `GET /summary` is `{ units, value, lowStock }`. `GET /lots` is a page of the lots that still hold units (sorted by `receivedAt`, product, SKU, code, available, unit cost, value). `GET /movements` is the stock ledger as a feed, `{ items, nextCursor }`, newest first (`kind`, `reason`, `sku`, `lotId`, `from`/`to`; `cursor`, `limit` up to 200); the filters are `movementFilters` (`src/lib/schemas/inventory.ts`), shared with `movements.csv`. `POST /adjustments` writes an adjustment (a stock count is one) or a waste on a lot.
- `GET /api/admin/audit-events` answers `{ items, nextCursor }` (newest first; `entityType` + `entityId`, `actor` user id, `verb` (`create`, `update`, `status` or `archive`), `action` exact or a prefix ending in `.` such as `order.`, `from`/`to` local days; pass `nextCursor` back as `cursor`, `limit` up to 200). `GET /api/admin/audit-events/actors` lists the staff who have acted, for the actor filter. `src/lib/schemas/audit.ts` lists the entity types and verbs the log can be filtered by, and `audit.test.ts` scans the server source and fails when the API writes one that is not listed.
- CSV (`GET /api/admin/exports/...`): `orders.csv` and `order-lines.csv` (the order list filters), `customers.csv` (`q`, `segment`, `marketing`), `campaign.csv` (`channel` = `email` or `whatsapp`, optional `segment`: name, the contact of that channel, segment, orders, last order and when the consent was given, only for customers who accept that channel), `movements.csv` (ledger filters), `reports/{sales,products,brands,losses,stock,customers,fulfillment,reorder}.csv` (the report parameters; `totals=true` adds a last `total` row to sales, products and brands, whose money comes from the exact sum, lot costs rounded once, so it can differ by a cent from the sum of the rounded rows). RFC 4180 with CRLF, UTF-8 with a BOM for Excel, money as decimals of the currency's minor unit (`1234.50`), instants as the store's local date and time (`2026-10-05 18:26:49`), text starting with `=`, `+`, `-`, `@`, tab or CR prefixed with `'` (formula injection; this includes phones such as `'+50371234567`). The CSVs read the list by cursor, page by page (not through the screens' offset pages); the first page is read before the response starts, so a failure is still an error answer. At most 10 exports per admin per minute (`EXPORT_LIMITER`, `429 rate_limited`).

### Reports

`GET /api/admin/reports/...` and the dashboard compute every figure with the same functions (`src/server/domain/sales.ts`, `reports.ts`, `reorder.ts`, read by `report-data.ts`), on whole local days of the store (`from`, `to` as `YYYY-MM-DD`, both included, at most 1,096 days; bounds by `startOfLocalDay`, DST-safe). Reports filter on indexed dates (`orders.shipped_at`, `orders.created_at`, `inventory_movements.created_at`, `returns.created_at`, `payments(kind, recorded_at)`; audit events by `(actor_user_id, id)`). Money is in minor units; lot costs are summed in `_e4` units and rounded once per reported figure, so a total can differ from the sum of its rounded rows by a cent.

- Sale: an order that left the store (`shipped` or `delivered`), dated by the local day of `shipped_at`, net of every return of its units whenever the return happened. Cancelled orders are not sales. Pending and paid orders are bookings, not sales yet.
  - `revenue` = what the order owes (`amountOwed`): merchandise + `shipping`.
  - `merchandise` = kept units x order price - the discount kept (in proportion to the kept value), spread over the lines by kept value with the largest remainder so lines add up to the order.
  - `shipping` = the fee, while at least one unit is kept.
  - `costOfGoodsSold` = landed cost (`lots.unit_cost_e4`) of the units that left their lots for the sale minus the cost of the units that came back (restocked or written off).
  - `grossProfit` = merchandise - cost of goods sold; `margin` = gross profit / merchandise (4 decimals, null without merchandise). Shipping fees are not product margin, and written-off returns are a loss of the day they were recorded (losses report), not of the sale.
  - `units` = kept units; products and brands also give `unitsSold` and `unitsReturned`.
- Every sale figure also gives `tax` (the IVA of each order in proportion to what it still owes: `tax_included` x revenue / total, rounded), `netRevenue` = revenue - tax and `averageTicket` = revenue / orders (null without orders).
- `sales?from&to&granularity=day|week|month`: totals and one row per period, empty periods included; weeks start on Monday, months on the 1st; `partial` marks a first or last period cut by the range.
- `products?from&to`, `brands?from&to`: the sale figures per variant (named as last sold, from the order line snapshot) and per brand as written on the order lines, by merchandise. Products also give `firstSoldOn` (the local day of the first shipped order with that variant, ever), `daysOnSale` (from the later of that day and `from` to `to`) and `unitsPerDay` = kept units / days on sale, so an older or pricier product does not win only by volume; the screen ranks by merchandise, units or units per day (`rank`).
- `losses?from&to`, by the local day each record was made, whatever the order's status: `returns` (count, units, value at order price before discount, by reason; lot cost restocked and written off), `refunds` (confirmed refunds by `recorded_at`), `writeOffs` (all `waste` movements by reason at lot cost: damaged, demo units, returns that could not be resold...), `adjustments` (net units and value of `adjustment` movements; negative is shrinkage) and `totalLoss` = write-offs - adjustments value.
- `stock?from&to`, on hand as of the store's today: `lowStockThreshold`, totals `onHand`, `value` (units at lot cost), `unitsSold`, `rotation`, `daysOfCover`, `outOfStock` and `lowStock` (active variants), and per variant (active, or with stock) `onHand`, `value`, `lowStock`, `outOfStock`, `unitsSold` (kept units of the range's sales), `averageOnHand` (the units before the range and at its end, from the ledger, halved), `rotation` = units sold / average on hand (null without stock) and `daysOfCover` = whole days the units on hand last at the range's pace (null without sales); sold out first, then low, then fewest days of cover.
- `customers?from&to` (who buys and how often): bought orders (paid, shipped, delivered) placed in the range valued at what they owe; `buyers`, `newBuyers` (first bought order ever inside the range), `returningBuyers`, `ordersPerBuyer`, `valuePerBuyer`, `frequency` (buyers with 1, 2 or 3+ orders), `segments` (every customer today per segment) and `topBuyers` (the first 20 by value).
- `fulfillment?from&to` (do we keep our promise): orders placed in the range in any status; `byStatus`, `averageDeliveryDays` and `medianDeliveryDays` (local days from order to delivery), `averageDispatchHours` (order to shipping), `deliveryDays` (0-1, 2, 3, 4, 5+), `onTimeRate` (delivered by `delivery_estimate_to`), `lateOrders` and `lateOpen` with the first 50 in `late` (delivered after the promise, or not delivered and past it today), `returnedOrders` and `returnRate` over shipped or delivered orders.
- `reorder?lookbackWeeks=8&targetWeeks[&leadTimeDays]` (lookback 1-52 weeks, default 8; target 1-52 weeks required), per active variant of a product that is not archived, most urgent first:
  - Supplier (`supplier`, with `source`): the variant's preferred active supplier item of an active supplier, else its only one; none when it has several and none is preferred. `leadTimeDays` is the query's `leadTimeDays` when given (an override for every variant, `leadTimeSource: "query"`), else the supplier's (`"supplier"`); when neither is known it is null, counted as 0 and flagged `lead_time_unknown`.
  - `unitsSold` = kept units of sales in the last `lookbackWeeks x 7` local days (`weeklyUnits`, oldest week first, weeks ending today); `daysObserved` = those days, or the days since the first lot was received when that is later, but never fewer than 14 days (or the whole lookback when shorter): a shorter history is spread over that window and flagged `short_history`, so a first day's sales are not extrapolated; `ratePerDay` = units sold / days observed.
  - `onHand` = units in the variant's lots; `committed` = 0 since orders take their units when placed (kept so the suggestion stays explainable); `backorders` = committed beyond on hand; `usable` = on hand - committed; `daysOfCover` = usable / rate; `stockoutOn` = today + whole days of cover.
  - `reorderPoint` = `variants.reorder_point` when set (the owner's minimum), else ceil(rate x lead time), the demand while an order is on its way; `orderUpTo` = reorder point + ceil(rate x 7 x target weeks); `gap` = order up to - usable.
  - `topUpQuantity` = the gap; without sales, the gap to the owner's reorder point, else the backorders. `orderQuantity` = the suggestion raised to the supplier item's minimum order and rounded up to whole packs (`rounded_to_pack_or_minimum`). `suggestedQuantity` = the top-up when usable <= reorder point (with no sales and no owner's point, only below 0), when orders wait for stock, or when the stock runs out within the lead time; else 0.
  - `unitCost` = landed cost of the latest lot bought at a price (free units excluded); `unitMargin` = current price - unit cost; `urgency` = 1 when usable stock is gone, else min(1, (lead time + 7) / days of cover); `priorityScore` = urgency x (units per week + backorders) x unit margin, in minor units (gross profit per week at stake), 0 when nothing is suggested and null when the margin is unknown. `reasons`: `backordered`, `below_reorder_point`, `stockout_within_lead_time`, `no_sales_in_lookback`, `no_cost`, `no_price`, `lead_time_unknown`, `short_history`, `rounded_to_pack_or_minimum`.
- Dashboard (`GET /api/admin/dashboard?from&to`, both or neither; without them the last 30 local days, today included): `sales` = the sales totals of the range (same as `reports/sales`, with IVA, net and average ticket), `byDay` its revenue, orders and gross profit per day, `topProducts` the first five of `reports/products` with `unitsPerDay`; `newCustomers` = customers whose first bought order falls in the range; `lowStock` = the first eight active variants at or below their point, with `daysOfCover`; `followups` = the overdue counts per action and the six most overdue; `pendingReviews` and `pendingStockAlerts`; `bookings` = orders placed in the range (`created_at`) that are not cancelled, valued at what they owe now; `losses` = the losses report of the range (write-offs count from the ledger, so a write-off of an order cancelled later still counts); `pendingOrders`, and `overduePendingOrders` = card and transfer orders past the payment deadline (follow-up action `collect_payment`); `stock` = the stock report totals (`onHand`, `value`, `lowStock`, `outOfStock`) and the store's `threshold`.

### Security

- `hono/csrf` on the whole API: form-like or body-less requests must come from the same origin (`Origin` or `Sec-Fetch-Site`); JSON requests from another origin need a CORS preflight the API never grants. Better Auth (`/api/auth/*`) checks the origin itself (a cross-origin sign-out with a session is `403 INVALID_ORIGIN`).
- Every response (pages and API) carries `Content-Security-Policy-Report-Only` (self only, inline scripts and styles allowed for TanStack Start hydration, `frame-ancestors 'none'`), `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` and a `Permissions-Policy`; `/api/admin` and `/api/auth` answers are `Cache-Control: no-store` (`src/server/security.ts`). No reporting endpoint is configured, so violations only show in the browser console: enforce the CSP after a pass through the live site with the console open.
- Request bodies: 16 KB on `/api/orders/*`, `/api/account/*` and on Better Auth's `/api/auth/*` (`src/server/auth-api.ts`, with or without a content length), 128 KB elsewhere (`413 payload_too_large`).
- New public orders are rate limited per client IP (`cf-connecting-ip`) with the Workers Rate Limiting binding `ORDER_LIMITER` (10 per minute, `wrangler.jsonc`; `429 rate_limited`); retries of an existing order are answered before the limit. Order lookups and code checks (`/orders/lookup`, `/promotions/validate`) use the same binding with their own counter per client (discount codes and order codes can be guessed), and the same 16 KB body limit. A public order without `cf-connecting-ip` (which Cloudflare and the local runtime always set) is refused with `400 client_ip_missing` (`src/server/client-ip.ts`), never counted under a shared key. CSV exports are limited per admin with `EXPORT_LIMITER` (10 per minute). The binding works in local dev; on Cloudflare it is available on the Free plan per its docs, not verified against a deployed Worker here.
- Better Auth reads the client IP from `cf-connecting-ip`, so sign-in and sign-up limits count real clients. Session cookies are Secure and HttpOnly.
- `preview_urls` is off and nothing is deployed yet (`workers_dev` is on, no custom domain). `wrangler.jsonc` has no comments, so scripts can read it as JSON; the reasons for its settings live here.

### Search engines

- The store layout (`src/routes/_store/route.tsx`, `storeHead` in `src/lib/seo.ts`) gives every store page its title and description, `rel=canonical` to its own URL in its own locale without search parameters (a filtered listing points at the listing), `hreflang` alternates `es` (no prefix), `en` (`/en/...`) and `x-default` (the Spanish URL), Open Graph (`og:locale` is `<language>_<country_code>`; default image `/og-default.png` or `/og-default-en.png`, 1200 x 630) and `twitter:card`. - Icons, `site.webmanifest`, the logo PNG and the preview images are in `public/`, generated by `scripts/brand_assets.py`, which still draws the previous brand's mark: the Nagomi assets are pending the storefront redesign.

### Migrations

- Nothing is deployed, so the migrations are regenerated freely: `drizzle/0000_baseline.sql` is every table, generated by drizzle-kit from `src/db/schema/` and `src/db/auth-schema.ts`, and `drizzle/0001_integrity_triggers.sql` is every trigger, the views `customer_segments` and `order_followups` and the one expression index, a custom migration (`bunx drizzle-kit generate --custom`) written for the D1 statement splitter: uppercase `BEGIN`/`END`, no `CASE` in trigger bodies or views (`iif()` instead), LF endings. Workflow: edit the schema, `bun run db:generate`, read the SQL, then `bun run db:reset && bun run db:migrate && bun run db:seed && bun run media:seed`.
- D1 binds JavaScript numbers as REAL: arithmetic on a bound number in SQL is a float operation (`cast(? as integer)` keeps an integer division), and batched selects need unique column names (D1 returns batch rows as objects keyed by name, so drizzle misplaces a repeated one: alias it with `.as()`).
- `src/db/migrations.test.ts` applies every migration to SQLite (foreign keys on) and fails when a trigger that a migration created is missing, when generated SQL rebuilds or drops a table, or when a trigger stops refusing what it should.
- Once a database has data to keep, changes are additive only: new tables, indexes and triggers, `ALTER TABLE ADD COLUMN` that is nullable or has a constant default (a default such as `now` fails on D1, drizzle issue #6408), `UNIQUE` as a separate `CREATE UNIQUE INDEX`. Read every generated SQL file: no `__new_` rebuilds, `DROP TABLE` or `PRAGMA foreign_keys` (a drizzle-kit rebuild copies table-qualified CHECKs that SQLite rejects, and a parent table's rebuild stops at its no-delete trigger). Rules that may evolve are triggers (`DROP TRIGGER` + `CREATE TRIGGER`), not CHECKs.

## Back office

The back office (`/admin`, rendered in the browser only; every call is checked again on the server) is thin routes over feature folders and a few shared kits.

### Structure

- **Routes** (`src/routes/admin/<module>/`): `route.tsx` (the breadcrumb and an `Outlet`), `index.tsx` (the list), `new.tsx` and `$id.tsx` where the module has them. A route reads the URL, starts the queries and renders a feature, nothing more. Brands and categories are one file each (create and edit are a dialog); sets are `/admin/bundles` (list, new, `$id`); order follow-up is `/admin/orders/followups`. Inventory is four routes (`/admin/inventory`, `/lots`, `/movements`, `/reorder`), settings five under link tabs (`/admin/settings/store`, `/payments`, `/promises`, `/pages`, each card its own form; the store tab includes the customer thresholds, follow-up hours and social links), reports eight (`/admin/reports` sales, `/products`, `/brands`, `/stock`, `/customers`, `/fulfillment`, `/losses`, `/reorder`, each opening with the question it answers, with the range in the URL, presets today, 7 and 30 days, this month and last month or a calendar range, and a CSV link). The overview is `/admin` (admin only; support lands on `/admin/orders` with the follow-ups on top).
- **Features** (`src/features/<module>/`): the screens (tables, columns, dialogs, editors), `queries.ts` (query options; keys start with `["admin", <module>]`), `mutations.ts` and `search.ts` (the defaults of the list and the link of its CSV).
- **Schemas** (`src/lib/schemas/<module>.ts`): the query of a list (page, sort, filters), its sort whitelist and the limits both sides check are one zod schema, imported by the Hono route (`validate("query", ...)`) and by the screen (`validateSearch`), so the address of a screen is the query the server validates. The body of a form has its schema next to the form.
- **Errors:** `src/lib/errors.ts` maps an API error code to a Paraglide message; `errors.test.ts` scans the server source for every `error: "code"` and fails when a code has no message, except the ones it lists as shown generically.

### Lists

- **Query:** `pagedSearch(sorts, defaults)` (`src/lib/list.ts`) gives `page`, `pageSize` (10, 25, 50 or 100; 25 by default), `sort` (one of the list's whitelist), `dir` and `q`; a list adds its filters with `.extend`.
- **Answer:** `Paged<T>` = `{ items, total, page, pageSize, pageCount }` (`toPaged`, `pageWindow` and `sortBy` in `src/server/domain/list-query.ts`). A page past the end is empty with the real total; `sortBy` orders by the chosen column and then by id in the same direction, so equal rows keep one order from page to page. Ledgers that only grow (stock movements, audit events, page versions, media files) are `Feed<T>` = `{ items, nextCursor }` with an id cursor instead.
- **One round trip:** the page and its `count()` run in one `db.batch`. D1 returns batch rows as objects keyed by column name, so columns that share a name (the ids of joined tables) are aliased with `.as()`.
- **State in the URL:** a list route has `validateSearch` (the same schema), `stripSearchParams(defaults)` (a default stays out of the address) and a loader that starts `prefetchQuery` without awaiting it, so the page renders at once, the table shows its own skeleton, and paging or filtering keeps the previous rows (dimmed) while the next page loads.
- **Table kit** (`src/components/admin/data-table/`): `DataTable` over TanStack Table 9 in manual mode (`useDataTable`: pagination and sorting are the server's, the table state is the URL's), `TableToolbar`, `TableSearch` (writes to the URL 300 ms after the last key), `SelectFilter`, `DateRangeFilter` (days of the store), `StatusTabs`, `TablePagination` and `RowActions`. It draws the skeleton rows, the error with a retry, "no results" with a way to clear the filters, and an `empty` slot for a list with nothing in it.

### Forms

- **Kit** (`src/components/admin/form/`): `useAppForm` (TanStack Form's `createFormHook`) with the fields `TextField`, `TextareaField`, `MoneyField`, `SelectField`, `CheckboxField`, `SwitchField`, `DateField`, `ComboboxField` (a search over a long list, on `command` and `popover`) and `MediaField` (`media-picker.tsx`: pick an uploaded image or upload one), plus `SubmitButton` and `FormError`. `LocaleTabs` repeats the same fields once per language, the default one first, and marks a tab whose fields have errors.
- **Validation:** every form passes `validationLogic` (`revalidateLogic()`: nothing is said until the first submit, then each change revalidates the whole form), its zod schema as `validators.onDynamic` and the API call in `validators.onSubmitAsync`. A refusal from the API comes back through `serverErrors`: `invalid_request` lists the paths that failed, each goes to its field, and the rest to `FormError`. Why `revalidateLogic`: a schema on `onSubmit` and `onChange` left its errors on fields the user had not touched, and the form then refused to submit without saying why.

### Shell and charts

- **Shell** (`src/components/admin/`): `AdminShell` (the shadcn sidebar, collapsible to icons on wide screens and a sheet on phones, its state kept in a cookie), `AppSidebar` (the sections, in `nav.ts`), `NavUser` (language, the store, sign out) and `AdminHeader`. Breadcrumbs come from the matched routes: `staticData.crumb` (a Paraglide message) or, for a route named by its data (an order's code, a product's name), the `{ crumb }` its loader returns (`LoaderCrumb`, `src/lib/route-data.ts`). Ctrl+K (Cmd+K on a Mac) opens `CommandSearch` (`cmdk`): the sections, and from two letters on the records of `GET /api/admin/search`.
- **Pages:** `PageHeader` (the title bar of a list or a record, with `HeaderActions`), `PageTabs`, `DetailPage` and `DetailColumns` (a record's page and its two columns), `QueryState`, `QueryError`, the skeletons (`DetailSkeleton`, `RecordNotFound`), `Panel` (a flat bordered card) with `Section` (the card with a header row; `Fact` is a label over its value) and `FormCard` (a card that is one form with its own save) built on it, `StatCard` with `StatGrid`, and `ChartCard`. Spacing comes from the `--spacing-admin-*` tokens of `styles.css`, which `cn` knows (`src/lib/cn.ts`), so a component's `p-admin-card` and a caller's `p-0` replace each other.
- **Charts:** one rule per form: bars compare a few categories (`kind="bar"`, or `"hbar"` for named products), a line shows change over time only from 7 points (`overTimeKind`, else bars), a pie (`ShareChartCard`, `share-chart.tsx`) shows parts of a total and refuses more than five, and tables give exact values (every chart also has a screen-reader table). `ChartCard` draws the shadcn `chart` (Recharts) from `series-chart.tsx`, loaded with `lazy()`: that chunk (about 340 kB, 101 kB gzip) is fetched when a chart is first shown and is not in the entry chunk (about 445 kB, 139 kB gzip; both measured with `bun run build` on October 25, 2026).
- **Audit labels** live in `src/features/audit/labels.ts`; the entity types and verbs they cover are `src/lib/schemas/audit.ts` (see the audit log above).

## Admin access

- Staff accounts are created with `bun run admin:create -- --email you@example.com --name "Your Name" [--role admin|support] [--remote] [--google-only]` (default role `admin`). The password comes from `ADMIN_PASSWORD` or is generated and printed once; it must have 10 to 128 characters. Customers create their own accounts at `/account/sign-up`; staff roles are never given through sign-up.
- `/admin` redirects to `/admin/login` without a session and accepts only staff (`isStaff`, `src/lib/roles.ts`: `support` or `admin`, not banned). Every `/api/admin/*` call is checked on the server (see "Staff roles").
- Google sign-in turns on when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set; it never creates users (only an existing staff account with the same email can use it). Password sign-in stays on, since customers need it. Redirect URI: `<BETTER_AUTH_URL>/api/auth/callback/google`.
- Sign-in is limited to 5 attempts and sign-up to 3 per minute per client IP (`cf-connecting-ip`), stored in D1; `get-session` is not counted. Sessions last 7 days. The admin plugin endpoints the back office has no screen for (create or update a user, set a role or a password, remove a user, impersonate) are in `disabledPaths` and answer 404; `src/lib/auth.test.ts` checks this and the sign-up and sign-in round trip against the real configuration. The Worker refuses to start when `BETTER_AUTH_URL` is not https and not localhost.
- Auth options live in `src/server/auth/options.ts` (app name Nagomi); what the Worker decides from its environment is in `src/server/auth/config.ts`; the hooks that normalize emails and link customers are in `src/lib/auth.ts`. After changing options, run `bun run auth:generate`, then `bun run db:generate` and the migration workflow.
- Secrets: `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` go in `.dev.vars` locally (gitignored) and in `wrangler secret put` for production. Generate a secret with `bunx auth@latest secret`.

## Production

Nothing is deployed; no remote command is run without the project owner's explicit authorization.

1. `bunx wrangler login`, then `bunx wrangler d1 create nagomi` and copy its `database_id` into `wrangler.jsonc` (the scripts use the `DB` binding).
2. `bun run db:migrate:remote`, then load the seed with `--remote`.
3. Enable R2, create the bucket with `bunx wrangler r2 bucket create nagomi-media`, then `bun seed/media.ts --remote`.
4. Set the secrets listed in `wrangler.jsonc` (`BETTER_AUTH_SECRET`, a new value, and `BETTER_AUTH_URL`, the https origin) with `bunx wrangler secret put <NAME>`, plus the optional `GOOGLE_*` values.
5. `bun run fonts`, then `bun run deploy`.
6. Password hashing (scrypt) needs more CPU than the Workers Free plan's 10 ms per request: customer sign-up and sign-in need the Workers Paid plan.
7. In `/admin/settings`, replace the placeholders (legal name, NIT, address, contact email, social links) and check the time zone, country, order prefix, thresholds and published promises.
