# Eclalune store

Storefront and back office for Eclalune, a personal care and beauty company in El Salvador. The code is country-neutral: currency, time zone, country, thresholds and copy about the business come from the database. Checkout currently sends the order to WhatsApp. Payments are recorded as rows (`payments`, with a unique provider transaction id), so a payment provider such as Wompi adds a webhook and rows, not a new model.

Scaffolded with the official TanStack CLI (`@tanstack/cli create`, add-ons: drizzle, paraglide, shadcn, tanstack-query, form, better-auth; deployment: cloudflare; toolchain: biome). Generated files keep their CLI conventions.

Note: `tanstack add <add-on>` re-applies the whole template and overwrites project files. Back up first and keep only the add-on's new files.

## Domain rules

The schema is `src/db/schema/` (store, one module per area) and `src/db/auth-schema.ts` (generated by the Better Auth CLI). Integrity rules drizzle-kit cannot express are triggers in `drizzle/0001_integrity_triggers.sql`; each abort a request can hit is answered as a 409 by `src/server/domain/db-errors.ts` (wired in `onError`, `src/server/app.ts`). Pure rules live in `src/server/domain/*.ts`, each with tests.

### Money, time and records

- Money is integers in the minor unit of the currency from `store_settings` (cents for USD; the number of decimals comes from Intl, so JPY has none and KWD three: `src/lib/money.ts`). Lot costs are integer hundredths of a minor unit (`unit_cost_e4`, `allocated_shipping_e4`) so shipping can be spread over units; reports round to minor units (`e4ToMinor`). The currency cannot change once an order or purchase order exists (`409 currency_locked`).
- Instants are UTC strings. Calendar dates (expiry, ordered/received on, delivery estimate) and every "today", day boundary and dashboard day use `store_settings.time_zone`; day boundaries are DST-safe (`startOfLocalDay`). Dates in requests must exist (`isCalendarDate`).
- Every enum is a CHECK on its column. Adding a value later means rebuilding that table, so treat the lists as fixed (see the migration rules below).
- Business records are kept for 10 years and never deleted: no foreign key cascades on store tables, and triggers refuse DELETE on orders, order lines (except while the order is pending), payments, returns and their lines, purchase orders and their lines (except while it is a draft), receipts and their lines, lots, audit events, consents and page versions. Brands, categories, concerns, products, variants, product images, routines and suppliers are archived, not deleted (triggers); a variant never moves to another product.
- Every admin write runs as one D1 `batch` (one transaction) together with its `audit_events` row (actor user id, action, entity type and numeric id, JSON data; codes and references go in the data). Actions are `<entity>.create`, `.update`, `.archive` or `.status` (with `from` and `to` in the data), e.g. `order.status`, `payment.create`, `return.create`, `inventory_movement.create`, `store_promise.status`; a payment's or return's event carries its `orderId`, so the order detail lists it (expression index `audit_events_order_idx`).
- Search ignores accents and case beyond ASCII (SQLite's `lower()` and `LIKE` fold ASCII only): searchable rows keep a `search_key` (NOT NULL) written by every API write path with `searchKey()` (`src/server/domain/search.ts`: NFD, combining marks removed, lowercase, single spaces; phones as their digits), and a term is normalized the same way before an escaped `LIKE` (`searchMatch`, `src/server/domain/search-sql.ts`). Keys: `orders` (code, the name given with the order), `customers` (name, email, phone digits), `brands` (name, slug), `product_translations` (name), `variants` (SKU, barcode), `suppliers` (name, contact name). The seed fills them. Admin searches match only the keys (products: name in the default locale, brand, SKU or barcode of any size, or the slug), so `creme`, `CRÈME` and `Crème` find the same rows. Names and titles per language have no key: the lists of categories, concerns, routines and collections match and sort them with `foldedText()` (`search-sql.ts`), which lowercases and replaces the Spanish accents (and `ñ`) in SQL, so "Ángel" sorts with the A's. Audit events, page versions and returns are never rewritten; a consent only gains its customer.

### Catalogue

- Admin API (every write in one batch with its audit event, named `<entity>.create`, `.update`, `.archive` or `.status`, a status change carrying `from` and `to`): `/api/admin/brands`, `/categories`, `/concerns`, `/routines`, `/products` (variants under `/products/:id/variants` and `/products/variants/:id`) and `/product-images`. The lists of brands, categories, concerns, routines and collections are pages (see "Back office", "Lists") with a `status` filter, `q` and a sort whitelist; each also has `GET /options`, the whole set as `{ id, name, status }[]` for the selects of other screens (names in the store's default language, archived ones included, the consumer filters; a category, concern, routine or collection with no text in that language is left out). `GET /products/list` is the product-level page (filters `status`, `brandId`, `categoryId`, `concernId`, `q`; sorts `name`, `brand`, `status`, `createdAt`, `priceFrom`, `stock`); `GET /products` is unpaged and per size, for the pickers. Nothing is deleted: `PATCH` with `status: "archived"`.
- Slugs are lowercase words joined by single hyphens, at most 80 characters (CHECK and API), unique per table (`409 duplicate_slug`). A product's slug changes only while it is a draft and a routine's while it is not published (`409 slug_locked`): published URLs stay stable.
- `products.status`: `draft` (never shown), `published` (for sale), `archived` (retired, keeps its history); a product is created as a draft. Transitions: draft to published or archived, published to draft or archived, archived back to draft. Publishing needs an active priced variant, the default locale's text and an active brand and category. A variant's price may be empty only while its product is a draft: a product cannot be inserted or updated to published without an active priced variant, and an active variant of a published product cannot lose its price or be archived if it is the last priced one (API check and triggers, `publish_requires_price`).
- A product points at an active brand, category and concerns (`409 reference_unavailable`). A brand or category used by a published product cannot be archived (`409 in_use`); an archived concern just leaves the storefront. Restoring an archived category or concern needs its name in the default locale (`409 publish_requires_default_translation`).
- Product text per locale: name, tagline, description, how to use, key ingredients, SEO title (70) and description (160); categories and routines also have SEO fields. `products.inci` (as printed, not translated) and `products.sanitary_registration` (shown only when set).
- The admin product list (`GET /api/admin/products`) gives per variant `onHand` (units in lots that can still be sold, by the store's date), `committed` (units held by open orders, see Orders), `available` (what can still be sold), `expired` (units in expired lots, separately) and `latestUnitCost`: the landed unit cost of the latest lot received at a price (free units left out; null until one was received), the same basis as the reorder report (`latestLandedCostE4`, `src/server/domain/inventory.ts`).
- `GET /api/admin/products/:id` also gives `publishMissing` (what still stops publishing, in this order: `text`, `price`, `photo_alt`, `brand`, `category`; empty when it can be) and, per size, `skuEditable` and `onHand` (units in every lot, expired ones too: what archiving the size would leave without a home). `POST /api/admin/products` takes an optional first `variant`, written with the product or not at all. `PUT /products/:id/translations` (`translations` by language) writes every language given in one batch and leaves the others as they are; it replaced the per-locale PUT. The editor saves each section as one write: fields, concerns and skin types (each the whole set) and status through `PATCH /products/:id`, the texts, one size, one photo.
- Variants are the sizes of a product: SKU (capitals, unique, `409 duplicate_sku`; it changes only while the product is a draft and the variant was never ordered or purchased, `409 sku_locked`, checked again inside the write), price, compare-at price (above the price), size, barcode, gross weight in grams and reorder point (on-hand units at or below which it needs reordering). The barcode is entered as printed (GTIN-8, -12, -13 or -14), its GS1 check digit is verified, and it is stored as GTIN-14, left-padded with zeros (CHECK, unique, `409 duplicate_gtin`). A variant on a draft, ordered or partially received purchase order cannot be archived (`409 in_use`); one with units on hand is archived only with `archiveWithStock: true` (else `409 variant_has_stock` with `onHand`).
- Routines: `draft`, `published`, `archived` like products, featured flag and position; steps are variants in order (`PUT /routines/:id/items`, active variants only). Publishing needs the default locale's text and at least one step; the storefront shows a routine only while every step is for sale.
- Catalogue text lives in `*_translations` tables with fallback to the default locale; creating a brand-new category, concern, routine or product needs the default locale's text. Store name, WhatsApp number, legal identity, legal pages, routines and all copy live in the database; the code holds no business data.
- Brands have page text per locale (`brand_translations`: description, SEO title and description; `GET /api/admin/brands/:id`, `PUT /api/admin/brands/:id/translations/:locale`, which replaces that locale's text). The admin product detail lists the collections the product is in (`collectionIds`; membership is edited from the collection).

### Collections

- `collections` (+ `collection_translations`: title, description, cover alt text, SEO title and description; `collection_products` with a position from 1, unique per collection): curated groups of products such as "The essentials", with the product lifecycle (`draft`, `published`, `archived`; created as a draft), a position, a `show_on_home` flag and an optional cover (a media file). Publishing needs the default locale's text and at least one product (`409 collection_requires_products`, checked again inside the write); the slug changes only while not published (`409 slug_locked`). A collection holds products that are not archived (API and trigger, `409 reference_unavailable`); the storefront shows only its published products, in the collection's order. Archived, never deleted (trigger).
- Admin API: `GET /api/admin/collections` (a page: `status`, `q`, sorts `title`, `position`, `products`, `home`, `status`), `GET /options`, `GET /:id`, `POST /` (slug, position, showOnHome, coverMediaId, translations with the default locale, optional productIds), `PATCH /:id` (slug, position, showOnHome, coverMediaId, status), `PUT /:id/translations/:locale` (replaces the text), `PUT /:id/products` (`productIds` in order; replaces them), `PUT /order` (`collectionIds`: every collection that is not archived, first to last; `409 collections_changed` otherwise). Audit: `collection.create`, `.update`, `.status`, `.archive`.

### Home slides

- `home_slides` (+ `home_slide_translations`: title, body, CTA label, image alt text): the home hero's slides (the storefront reads none yet: its hero is one fixed photo, no carousel since October 18, 2026), with the product lifecycle, a position, a desktop image and an optional mobile image (media files), a link and optional start and end dates (local days of the store, both included). The storefront shows published slides within their dates, by position. The link is a storefront path without the locale prefix (`/products?category=sunscreen`; the storefront adds `/en`), checked by `isStorePath` (`src/server/domain/store-path.ts`: one leading `/`, printable ASCII without spaces or backslashes, at most 300 characters, not `/api`, `/admin`, `/media` or a locale prefix) and by a CHECK. Publishing needs the default locale's text. Archived, never deleted.
- Admin API: `GET /api/admin/home-slides[?status]` (all of them, not paged: the list is short), `GET /:id`, `POST /` (desktopMediaId, mobileMediaId, linkPath, startsOn, endsOn, position, translations with the default locale), `PATCH /:id` (those fields and status), `PUT /:id/translations` (`translations` by language; each language given is replaced as a whole, title and imageAlt required, in one batch, and the others are left as they are; it replaced the per-locale PUT), `PUT /order` (`slideIds`: every slide that is not archived). Audit: `home_slide.*`.

### Storefront catalogue

- The store page (`GET /api/products`) reads the whole published catalogue in one D1 batch and refines it in memory (`src/server/domain/storefront-catalog.ts` loads it; `catalog-query.ts` is the pure filtering, faceting, sorting and paging, with tests), which stays cheap for a catalogue of hundreds of products. A product shows its cheapest active priced size (price, compare-at price, size and SKU on the card) and the number of sizes.
- Search (`q`) ignores accents and case: every word must appear in the product's brand, name (the page's locale and the default one), category, concerns, key ingredients or SKUs. Refinements: `category`, `concern`, `brand`, `collection` (repeat a parameter for several values; values of one refinement are alternatives, refinements narrow each other), `minPrice`/`maxPrice` (minor units, both included, on the card's price) and `availability`.
- Availability follows the stock: a size is `in_stock` while it has sellable units (see Orders, "Stock"), else `sold_out` and it cannot be ordered ("Agotado"). Each size carries `maxQuantity`, its sellable units up to `max_quantity_per_line`, so the exact stock above that limit is not published. A card shows the cheapest size in stock, else the cheapest; a product is `in_stock` when any size is.
- Facets: each value counts the products matching every other refinement but not its own facet's (standard faceting); a facet lists the values found among the products matching the search, plus the selected ones; `priceRange` is that of the products matching everything but the price.
- Sorts: `featured` (in stock first, then routine step, then name; with one collection chosen, the collection's order), `newest` (creation, newest first), `price_asc`, `price_desc`, `name` (in the page's locale).
- Related products (`src/server/domain/related.ts`): at most 8, never the product itself; a step of the same published routine weighs most, then each shared concern, then the same category or another routine step; at most two per category while others are left; each marked `alternative` (same routine step) or `complement`.

### Media

- Images (product photos, home slides, collection covers, editorial photos) live in the R2 bucket bound as `MEDIA` (`wrangler.jsonc`) under a content-addressed key, `<sha256>.<ext>`, and are served by the Worker at `GET /media/<key>` with the stored type, `Cache-Control: public, max-age=31536000, immutable` and the hash as a strong `ETag` (a matching `If-None-Match`, compared weakly, is answered 304 without reading R2; `*` answers 304 when the object exists). Anything that is not such a key is a 404 (`src/server/media.ts`).
- Upload: `POST /api/admin/product-images`, multipart with `file`, `productId`, `kind` (`packshot`, `lifestyle`, `texture`), optional `variantId` (the photo then shows only for that size; a trigger keeps it a size of the same product) and alt text as `alt.<locale>`, the default locale required. JPEG, PNG, WebP or AVIF up to 5 MB and 10,000 px on a side (`415 unsupported_image_type`, `413 image_too_large`); the type and pixel size are read from the file itself, and a file that is not what it declares or is incomplete (a PNG without IDAT and IEND, a JPEG without its scan, a WebP or AVIF whose boxes do not fit) is `400 invalid_image` (`src/server/domain/images.ts`; JPEG EXIF rotation swaps width and height). The same photo twice on a product is `409 duplicate_image`. A body that is not a multipart form is `400 invalid_form` (also for `POST /api/admin/media`). Resize photos before uploading (about 1600 px); there is no server-side resizing.
- `PATCH /api/admin/product-images/:id` changes kind, size, status (archive) and alt texts (the default locale's cannot be removed); `PUT /api/admin/product-images/order` sets the order of all the product's active photos. A photo's file and product never change (trigger). Archived photos stay in R2: a key is never reused for other content.
- The storefront returns each photo's URL, kind, width, height and alt text in the page's locale, else the default locale's, else the brand and product name (an accessibility fallback for data that slipped past the checks, never an error), and renders them with `width` and `height`. Publishing a product, and restoring an archived photo, need alt text in the default locale on every active photo (`409 image_alt_required`); changing the default locale is refused while a published product's photo has no alt text in it.
- Every image file is a `media_files` row (content key, type, size in bytes, pixel size; a row never changes and is never deleted, and its key is a content key, CHECK). A product photo (`product_images`) points at its file with `media_file_id` and adds the product, size, kind, order, status and alt texts, so one file can be a photo of several products; uploading a product photo registers its file when it is new. Home slides and collection covers reference a file by id, uploaded with `POST /api/admin/media` (multipart `file`; the same file again answers its existing row with 200); `GET /api/admin/media` (newest first, `cursor`/`limit`, answers `{ items, nextCursor }`), `GET /api/admin/media/:id`, `GET /api/admin/media/:id/usage` (where the file is shown: the home slides that use it as wide or phone picture, the collections it covers and the product photos made from it, archived ones included; names in the store's default language, null without text in it). Audit: `media_file.create` (a product photo's `product_image.create` carries its file's key and size).
- Seed photos are in `seed/images`; `seed/build.ts` registers the ones `seed/catalog.json` names, with their R2 key, size and alt text (brand and product name), and `bun run media:seed` uploads them to the local bucket (`bun seed/media.ts --remote` for production). Editorial photos are in `seed/editorial` with `manifest.json` (file, alt text per locale, credit, source and license): every file of the manifest becomes a media file, as does every product photo (a file used twice is one row), `seed/home.json` (slides) and `seed/collections.json` (collections, products by slug) point at them by file name, and the build fails when a file, an alt text or a referenced product is missing. R2 serves them; the only static copies are `hero-2`, `hero-4` and `editorial-1` in `public/editorial/`, used by the fixed home hero and the company page.
- Each `/media` request is a Worker request (static assets are not), counted in the plan's request limits. If that becomes a cost, serve the bucket on its own custom domain (for example `media.eclalune.com`) and change `mediaUrl`.

### Stock

- Stock is never stored: it is the sum of `inventory_movements` per lot. The ledger is append-only (corrections are new movements) and a trigger refuses any movement that would take a lot below zero (`lot_balance_negative`, answered as 409 `stock_changed`; the whole batch rolls back, so a stale read can never oversell).
- Movement kinds: `receive` and `return` (positive), `sale` and `waste` (negative), `adjustment` (either sign; a stock count is an adjustment with the reason `count_difference`). A sale points at its order line (only while the order is confirmed, never more units than the line, only from a lot of the line's variant); a return, and the waste of a written-off return, point at the return line. `waste` and `adjustment` need a reason (`expired`, `damaged`, `sample_tester`, `own_use`, `lost_theft`, `count_difference`, `customer_return`, `other`; `other` needs a note).
- Lots carry their code, expiry and landed unit cost. An expiry printed as a month ("EXP 2027.05", entered as `2027-05`) is stored as the month's last day with `expiry_precision = 'month'` and shown as the month. A lot sells through its expiry date, never after it.
- Fulfilment allocates units FEFO (earliest expiry first, ties by lot id, expired lots skipped) using the store's local date.

### Purchasing

- Suppliers (`/api/admin/suppliers`): name unique ignoring case (`409 duplicate_name`, checked again inside the write), contact name, phone (stored in E.164, read in the store's country), email (trimmed and lowercased), payment terms and notes as text, and `lead_time_days` (days from placing an order to having the units; null until the supplier states it, never below 0); archived, never deleted. New purchase orders, and placing a draft, need an active supplier (`409 supplier_archived`, API and triggers); an archived supplier's open orders can still be received or cancelled. Blank notes on purchase orders and receipts are stored as null (CHECK on purchase orders). `GET /api/admin/suppliers` is a page (sorts `name`, `leadTimeDays`, `openPurchaseOrders`, `createdAt`; `status`; `q` = name or contact), `GET /options` is the whole set as `{ id, name, leadTimeDays, status }[]` (`?status=` narrows it; a purchase order lists archived ones too) and `GET /:id` adds `openOrders`, the supplier's purchase orders that are draft, ordered or partially received.
- Supplier items (`supplier_items`): what a supplier sells of a variant, one row per supplier and variant (`409 duplicate_supplier_item`), with the supplier's code, `pack_size` (orders are whole packs) and `min_order_quantity`, each null while not known; archived, never deleted, and the supplier and variant never change (triggers); only created for an active supplier. At most one active item per variant is preferred (partial unique index); marking one preferred moves the flag in the same batch; asking for an archived item, or one of an archived supplier, to be preferred is `409 supplier_item_archived` or `409 supplier_archived`, and archiving the preferred item drops the flag. API: `GET /api/admin/suppliers/items?variantId&supplierId&status`, `POST /api/admin/suppliers/:id/items`, `PATCH /api/admin/suppliers/:id/items/:itemId` (code, pack, minimum, preferred, status), audited. The seed links the supplier to the variants of its purchase order with no lead time, pack or minimum.
- Purchase order: `draft -> ordered -> partially_received -> received`; `draft`, `ordered` and `partially_received` can be cancelled (for a partial one: the rest will not come). A reference is unique among the supplier's purchase orders that are not cancelled, so a cancelled draft frees it. Several lines may share a variant (e.g. free units at cost 0). A draft can be corrected (`PATCH /api/admin/purchase-orders/:id`: reference, notes, tax treatment, lines and costs); lines are fixed once receiving starts and never drop below what arrived. The status always matches the receipts (trigger `purchase_order_status_mismatch`). Purchase orders are mounted at `/api/admin/purchase-orders`: `GET /` is a page (sorts `createdAt`, `reference`, `supplier`, `status`, `total`, `orderedOn`; filters `status`, `supplierId`, `from`/`to` local days of creation; `q` = reference or supplier), `GET /:id` is the order with its lines, what arrived of each and every delivery with the lots it created, `POST /` creates an order (a draft, or ordered when `orderedOn` is given), `POST /from-reorder` (`supplierId`, `variantIds` and the reorder parameters) creates a draft for one supplier from the reorder suggestions (`409 nothing_to_order` when none applies; a size never bought starts at cost 0, to be filled in; the reference is the day's date, with `-2`, `-3` when the supplier already has one that day) and answers `{ id, reference }`, and `POST /:id/order`, `/:id/cancel` and `/:id/receive` move it along.
- A receipt is one delivery (`received_on`, supplier invoice reference, shipping cost, required even when 0). It cannot be dated after the store's today or before the order date, and a lot already expired on arrival is refused (`lot_expired_at_receipt`). Each receipt line creates exactly one lot and its single `receive` movement of the same quantity. Receipts go only into `ordered` or `partially_received` orders and never beyond the units still expected (trigger `receipt_exceeds_ordered`); the order status is recomputed from what arrived. A receipt's order, date and shipping cost cannot change afterwards.
- Landed cost: the receipt's shipping is spread over its lines by line value (units x supplier unit cost; by units when every line is free) with the largest-remainder method, so the shares add up exactly. A lot's unit cost is (supplier cost x units + its share) / units, rounded half up to a hundredth of a minor unit (at most half a hundredth of a cent per unit off the invoice). Lot costs cannot change after the fact. Whether supplier prices include IVA is recorded per purchase order (`tax_included`); IVA paid while not IVA-registered is part of cost.

### Orders

- Status machine (`src/server/domain/order-state.ts`, same table in a trigger): `pending -> confirmed -> fulfilled -> delivered`; `pending` and `confirmed` can be `cancelled`; `fulfilled` can be cancelled only when delivery failed, which records a return (reason `delivery_failed`) restocking every unit to the lot it left from, in the same batch (a trigger refuses the cancel while units are still out). Returns of delivered orders do not change the status.
- Creating an order (public WhatsApp checkout or admin) needs an idempotency key (a UUID from the client, stored lowercase, so any case is the same key) stored with a SHA-256 of the normalized request: a retry returns the stored order, the same key with another body is a 422 `idempotency_key_reused`.
- Order lines snapshot the SKU, brand, product name (default locale), size and unit price, so catalogue edits never rewrite a sale. A pending order's lines and notes can change (`PATCH /api/admin/orders/:id`: kept lines keep their price, added lines take the published price, the subtotal is recomputed in the same batch, and an order placed with a discount code gets the code's discount on the new subtotal; below the code's minimum the edit is `409 promotion_min_subtotal` unless `removePromotion: true` drops the code and its discount); after that they are fixed. The subtotal must equal the lines when the order is confirmed (`order_subtotal_mismatch`). Quantities per line are limited by `max_quantity_per_line` for public and admin orders.
- A public order may carry the customer's phone (`orders.customer_phone`, E.164, never changes; trigger) for order lookup and per-customer code limits; the customer is still linked at confirmation.
- The order's code, idempotency key, request hash, locale, channel and creation time never change; `confirmed_at`, `fulfilled_at`, `delivered_at` and `cancelled_at` are written once, by the status change they belong to.
- Confirmation (consumer law: by the next calendar day) fixes the payment method (one the store accepts), shipping method (`pickup`, `own_delivery`, `courier`), zone and its name, the shipping fee (the zone's fee, waived from the zone's free amount on subtotal minus discount; entered by hand when there is no zone, and refused together with a zone; pickup is free unless a fee is given), the discount (omitted: the order keeps the one it has, its code's or none; given: the whole discount, with its reason), the delivery estimate (one date or a range, never starting before the store's today), the delivery address, the customer (name and phone), and the exact confirmation text (`src/server/domain/confirmation.ts`, in the order's locale, listing every line, subtotal, discount, shipping, total, payment and delivery time). After confirmation these terms, the address, the zone name, the discount reason and the customer name cannot change (trigger `order_terms_locked`). `total = subtotal - discount + shipping` is a CHECK.
- `delivered_at` starts the return window (`store_settings.return_window_days`).
- Stock (`src/server/domain/stock.ts`, decided October 18, 2026: nothing is sold without units): a size sells at most its sellable units, the units in lots that have not expired minus the units held by open orders. A confirmed order holds its units until it is fulfilled or cancelled; a pending order holds them until its confirmation deadline (placed since the start of yesterday in the store's time zone, the boundary the dashboard uses for overdue orders), so an abandoned pending order stops holding without a job, and cancelling releases at once. The public order, the admin's create, edit and confirm check it before writing (`409 insufficient_stock` with what is left of each line: `items` of `{ sku, available }` for the storefront, `lines` of `{ variantId, sku, requested, available }` for the admin) and again inside the batch that writes (`stockFits`, `src/server/domain/inventory.ts`): a D1 database runs one query at a time and a batch is one transaction, so two orders never both take the last unit. Trigger `orders_confirm_within_stock` (`drizzle/0001_integrity_triggers.sql`) is the backstop: a confirmation never exceeds the units of all the size's lots plus what other confirmed orders hold. Waste, a count or an expiry can still leave fewer units than were promised; fulfilling then answers `409 insufficient_stock` as before.
- Customers are identified by phone in E.164, normalized with libphonenumber-js in the store's country (`7123-4567`, `+503 7123 4567` and `50371234567` are one customer); an existing customer keeps the stored name. WhatsApp orders keep the name given (`customer_name`) and are linked to a customer at confirmation (the customer row is written only when that confirmation wins).
- A legal or help page's text is `page_versions` (page, locale, version, title, body, who, when), append-only: every save is the next version and the current text of a locale is its latest one (`currentPageTexts`, `src/server/domain/pages.ts`); the seed writes version 1.
- Checkout requires acknowledging the privacy notice and the terms (cart checkboxes linking to both pages) and offers optional WhatsApp offers. The order stores three `customer_consents` rows (`privacy_notice`, `terms`, `marketing_whatsapp` granted or not), each pointing at the exact page version shown (the latest in the order's locale, else the default locale); they get the customer when the order is linked to one. The current consent of a customer is the latest row per purpose. The order API returns the consents with page, locale and version.
- The checkout is closed (`503 checkout_not_configured` with the missing fields, `store.checkoutOpen = false`) until the WhatsApp number, the legal identity (legal name, tax ID label, tax ID, address) and published `privacy` and `terms` pages with a version are there.

### Promotions

- `promotions` (+ `promotion_translations`: the public description, the default locale's required): a discount code (stored in capitals, 3 to 32 letters, digits, `-` or `_`; customers type it in any case), `percentage` (whole percent, 1 to 100) or `fixed` (minor units), an optional minimum subtotal, optional start and end dates (local days of the store, both included), an optional limit of uses in total and per customer, and a status `active`, `inactive` (created so by default) or `archived`. Archived, never deleted.
- The discount (`src/server/domain/promotions.ts`, tests): a percentage of the subtotal rounded half up to the minor unit, or the fixed amount but never more than the subtotal (the total never goes below the shipping), nothing below the minimum. Applied when the order is placed (`orders.discount`, the code as `discount_reason`, `orders.promotion_id`); shipping is still waived from subtotal minus discount.
- Uses are the orders placed with the code that were not cancelled (a cancelled order frees its use); per customer, those placed with the same phone or linked to the customer with it, so a limit per customer needs the phone at checkout. The checks run in the API (typed reasons) and again in the database when the order is written (triggers `orders_promotion_active`, `_usage_limit`, `_customer_limit`, `_discount_insert`), so concurrent orders on D1 cannot exceed a limit (`409 promotion_limit_reached`, or `promotion_unavailable` / `promotion_changed` when the code changed meanwhile). Dates are checked by the API (the database has no time zone).
- Once an order used a code, its code, type, value and minimum never change (`409 promotion_in_use`; trigger), so an order's discount is always derivable from them; dates, limits, status and descriptions can change. While an order is pending its discount follows the code's terms (trigger); the code can only be removed from it, while pending, and the discount with it.
- Admin API: `GET /api/admin/promotions` is a page (sorts `createdAt`, `code`, `usage`, `startsOn`, `endsOn`; `status`; `q` = part of the code) whose rows carry `usage`, `termsLocked` (true once any order used the code, cancelled ones included: its code, type, value and minimum are then fixed) and the descriptions, `GET /:id` (with the latest 50 orders that used it), `POST /`, `PATCH /:id` (also takes `translations`, written with the fields in one batch), `PUT /:id/translations/:locale` (`description`). Audit: `promotion.create`, `.update`, `.status`, `.archive`.

### Payments and returns

- `payments` rows are money in (`kind = 'payment'`) or out (`kind = 'refund'`), positive amounts, status `pending`, `confirmed` or `failed`, with method, reference, a provider transaction id (unique when present), recorder and time. A row is final once out of `pending`. Refunds never exceed confirmed payments (trigger). A refund for a return points at it, and that return belongs to the same order (trigger).
- What an order owes is derived (`amountOwed`, `src/server/domain/payments.ts`): nothing for a cancelled order; otherwise the units kept (not returned) at their order price, minus the discount in proportion to the kept value (rounded half up), plus the shipping fee while at least one unit is kept. When every unit came back nothing is owed, so a full return also refunds the shipping; a partial return keeps it. (Rule for Wilmer to confirm.)
- The payment status is derived from what is owed and the confirmed payments and refunds, never stored: `unpaid`, `partially_paid`, `paid` (what the store holds equals what is owed, including after an overpayment or a return was refunded), `refund_due` (the store holds more: overpaid, returned or cancelled after paying), `refunded` (nothing owed, everything given back) or `nothing_due`. "Mark paid" (`POST /api/admin/orders/:id/mark-paid`) records a payment for exactly the balance, so returned value is never charged. `POST /api/admin/orders/:id/refunds` records a refund of at most the refundable amount (`refund_exceeds_refundable`), optionally for a return of the order. Both are written only while the order's payments, refunds and returns are as read.
- A return (`returns`: order, reason, note, who, when) has lines per order line and lot with a disposition: `restock` puts the units back in that lot, `write_off` brings them back and records them as `waste` with reason `customer_return`. Returns are only for fulfilled or delivered orders and never exceed what left that lot for that line (trigger); a return line's ledger rows never exceed its quantity, and only `write_off` lines have waste. When a line left from several lots, the lot must be chosen. A unit cannot be restocked into a lot that has expired (`restock_expired_lot`): it is written off. Cancelling a fulfilled order (delivery failed) returns every unit still out, written off when its lot has expired meanwhile; when every unit already came back it is just cancelled.

### Invoices

- A sale is invoiced with a Factura (DTE 01) through GreenerSys (`src/server/integrations/greenersys.ts`, contract v1), the e-invoicing API Wilmer contracted. Rules and sources: [electronic invoicing research](../docs/research/2026-10-31-electronic-invoicing.md).
- **When:** the Factura is due when the buyer pays or receives the goods, whichever comes first. `confirm` with `paid`, `mark-paid` and `deliver` add a `queued` row to `tax_documents` **in their own batch** (`queueInvoice`, `src/server/invoicing.ts`), guarded by the batch's guard and by "no live Factura" (one per order, partial unique index `tax_documents_live_invoice`); right after the batch the route sends it. Nothing is queued while `GREENERSYS_API_URL` or `GREENERSYS_API_KEY` is empty. A counter sale (`in_person`) paid at confirmation waits up to 8 s for the seal.
- **Body** (`src/server/domain/invoicing.ts`): one line per kept unit group with our SKU as `codigo`, a description (brand, product, size) and the unit price **without IVA** to 4 decimals (catalogue prices include IVA); discounts go into the line prices (the API's global discount has 2 decimals and would miss a cent); shipping is its own line; `pagos` carries the order's total with Hacienda's payment code (transfer 05, cash and cash on delivery 01, payment link 99). The provider refuses a body whose `pagos` differ from its total, and a provider total that differs from the order's is flagged in `error`. No buyer data unless the customer asked for an invoice in their name (CT Art. 119-G).
- **Statuses:** `queued` (not taken yet: a credential, rate-limit or network problem is noted in `error` and the cron resends the same body and `Idempotency-Key`), `processing` and `contingency` (emitted, seal on its way), `sealed`, `rejected` (Hacienda; reasons in `rejection`), `failed` (the provider refused the body; nothing was emitted), `voided`. A new Factura for the order is possible after `rejected`, `failed` or `voided`, with the next key (`<order code>-01-<n>`). Triggers (`drizzle/0004_tax_documents_triggers.sql`): status only forward, identifiers fixed once known, rows permanent.
- **Cron** (`scheduled` in `src/server.ts`, every 5 minutes): sends queued rows, polls unsealed ones, and copies the signed JSON and the PDF of sealed ones into the private bucket `DOCUMENTS` (`dte/<YYYY-MM>/<generation code>.json|pdf`), in batches that stay under the Free plan's 50 subrequests.
- **Void:** `POST /api/admin/invoices/:id/void`, tipo 2 (the sale is undone), within 3 months of the seal (`voidDeadline`), with the real person responsible. Goods returned after delivery need the Evento de Retorno, not in the provider's API yet.
- **Buyer's copy:** `GET /f/<token>` (PDF) and `/f/<token>/json`, only for sealed documents; the admin copies the link into WhatsApp.
- Admin API `/api/admin/invoices`: the list (`invoiceListSearch`), `/attention` (counts that need a person), `/connection` (enabled document types), `POST /orders/:id` (issue now, optionally with `receptor`), `/:id/refresh`, `/:id/void`, `/:id/json` and `/:id/pdf`.

### Shipping

- `shipping_zones` (+ translations): method, fee, optional free-shipping amount, delivery days, position, active or archived. Admin API: `GET /api/admin/shipping-zones` is a page (sorts `position`, `name`, `method`, `fee`, `deliveryDays`; filters `status` and `method`; no `q`), `GET /options` the active zones with their fee and delivery days, unpaged (the order confirm dialog reads it, `activeZonesQuery`), `GET /:id`, `POST` (slug, fields and translations, the default locale required), `PATCH /:id` (fields; archive with `status: "archived"`; restoring needs the default locale's name, `409 publish_requires_default_translation`), `PUT /:id/translations/:locale`. Confirmed orders keep the fee and name they were given. The storefront advertises "free shipping from X" only when every active delivery zone waives the fee from the same amount; otherwise (and while no zone exists) it says shipping is confirmed on WhatsApp.

### Settings and promises

- Store rules are `store_settings` columns, edited in `/admin/settings`: `time_zone` (IANA), `country_code` (ISO 3166-1 alpha-2, also the default phone region), `tax_id_label`, `order_code_prefix`, `max_quantity_per_line`, `min_shelf_life_days` (receiving warning), `expiry_warning_days`, `return_window_days` (null when no window is stated). Accepted payment methods are rows of `store_payment_methods`. The API answers `503 store_not_configured` while a required setting is empty; nothing falls back to a value in code.
- Prices and dates use the Intl locale `<language>-<country_code>` (USD renders as `$24.00` in both languages).
- Blank text settings are stored as null. Changing `default_locale` is refused (`409 default_locale_untranslated`, with the list) while a published product, promise, page or routine, an active shipping zone, or a category or concern that is active or used by a published product has no text in the new locale, since every text falls back to it.
- The seed reads `settings.whatsappNumber` (E.164 in `seed/catalog.json`, stored as digits) and `settings.legalName`; the tax ID and address are still filled in `/admin/settings`, so checkout stays closed until then.
- Store promises (`store_promises` + translations) hold facts only and are published when true. Text may say `{return_window_days}`; such a promise cannot be published, nor the window cleared, while the setting is empty. `products.sanitary_registration` is shown on the product page only when set.
- Admin API (`/api/admin/settings`): `GET /` and `PATCH /` (the rules above and the accepted payment methods), `GET /promises`, `PATCH /promises/:id` (published or not), `PUT /promises/:id/translations/:locale`, `GET /pages` (each page with its current text per language, including that text's `version` and `createdAt`), `GET /pages/:id/versions?locale` (every text the page has had in that language, newest first, with the `author` of each save, null for the seed's; `{ items, nextCursor }`, `cursor`, `limit` up to 50) and `PUT /pages/:id/translations/:locale` (saves the next version).

### Storefront API

Public, under `/api`; texts in `locale` (`es` or `en`) with fallback to the default locale; money in minor units; instants UTC.

- `GET /store`: name, currency, default locale, country, time zone, WhatsApp number (digits) and `whatsappDisplay`, `freeShippingFrom`, `maxQuantityPerLine`, `returnWindowDays`, `checkoutOpen`, payment methods, published promises per locale, and `business` (legal name, tax ID label and number, address, phone, email).
- `GET /home?locale`: `slides` (live, in order: title, body, CTA label, link path, `image` and `mobileImage` with url, width, height and alt), `collections` (published, marked for the home, with products: their first 8 cards), `featuredRoutine` (or null), `categories` (with published products: name, count and a packshot) and `promises`.
- `GET /products?locale&q&category&concern&brand&collection&minPrice&maxPrice&availability&sort&page&pageSize` (page size up to 60, default 24; query values are strings, so the typed client passes `page: "2"`, `minPrice: "1500"`, and a repeated refinement as an array): `items` (product cards), `total`, `page`, `pageSize`, `pageCount`, `facets` (`category`, `concern`, `brand`, `collection`: slug, name, count, selected; `availability`: value, count, selected) and `priceRange`.
- `GET /products/:slug?locale`: every text (description, how to use, key ingredients, SEO), INCI, sanitary registration, brand, category, concerns, sizes for sale (cheapest first, each with availability), photos (with the SKU they are limited to, or null), routines and collections it is in, `related` (cards with `relation`). 404 unless published.
- `GET /navigation?locale`: the header menu, `categories`, `concerns`, `brands` and `collections` that have published products (slug, name, `productCount`), in the store's order; the same values and counts as the unrefined facets of `/products`, counted in SQL (`src/server/domain/navigation.ts`) instead of reading the whole catalogue.
- `GET /brands?locale` (active brands with published products: description, SEO, product count), `GET /brands/:slug?locale` (404 unless it has a published product, like the list); a brand's products are `GET /products?brand=<slug>`.
- `GET /collections?locale` (published, with published products), `GET /collections/:slug?locale` (all its published products in order; 404 unless it has one).
- `GET /routines?locale`, `GET /routines/:slug?locale`: published routines whose every step is for sale, steps in order (the size and its product card) and the total.
- `GET /catalog?locale`: every size for sale, one row each, in stock first, with `availability` and `maxQuantity` (the cart prices its SKUs and clamps its quantities with it).
- `GET /pages/:slug?locale`: a published legal or help page.
- `POST /promotions/validate` (`locale`, `code`, `items` of SKU and quantity, optional `phone`): `{ valid: true, code, type, value, description, subtotal, discount, total }` or `{ valid: false, code, reason, minSubtotal, subtotal }` with reason `not_found`, `not_started`, `expired`, `usage_limit_reached`, `phone_required`, `customer_limit_reached` or `min_subtotal_not_met`. `409 product_unavailable` when a SKU is not for sale.
- `POST /orders/whatsapp` (`idempotencyKey`, `locale`, `items`, optional `customerName`, `phone` and `promotionCode`, `consents`): `{ code, whatsappUrl, subtotal, discount, promotionCode, total }` (total before shipping; 201 new, 200 retry, also after the units are gone). A code that does not apply is `409 promotion_invalid` with its `reason`; lines beyond stock are `409 insufficient_stock` with `items` (see Orders, "Stock"), and nothing is written. The WhatsApp text lists the code, its discount and the total before shipping.
- `POST /orders/lookup` (`code`, `phone`): the order's status, `timeline` (placed, confirmed, paid, shipped, delivered, cancelled), delivery estimate, shipping and payment method, lines, subtotal, discount and code, shipping, total and `payment` (status, owed, paid, balance); no personal data. A wrong code or phone is the same `404 order_not_found`.

### Back office API

- Orders: `GET /api/admin/orders` is a page (`page`, `pageSize`, `sort` = `createdAt`, `code`, `customer`, `total` or `status`, `dir`, `q` = code, customer name or phone digits; filters `status`, `paymentStatus` (derived, see Payments), `channel`, `from`/`to` local days of `created_at`). The payment status filter runs in SQL (`paymentStatusIs`, `src/server/domain/order-sql.ts`: `amountOwed` and `paymentSummary` written as a condition on `orders.id`; `order-sql.test.ts` checks that both give every order the same status), so `total` counts it and a page is never short. A row has no lines. `POST /api/admin/orders` answers `{ id, code }`. `POST /:id/cancel` takes an optional `reason` (up to 200 characters), stored as `cancel_reason`, in the audit data and, for a fulfilled order whose delivery failed, as the note of the return it records. `GET /api/admin/orders/:id`: the order with its customer, lines (snapshots, returned units, lots each line left from), payments, refunds, returns with their lines, every ledger row of the order by lot, consents, audit trail and its landed cost (sold, returned, written off). A confirmation is written only while the order still has exactly the lines it was built from (ids and every field the text shows, compared as one JSON parameter), so the stored text always lists the lines. A return answers with its own id (`RETURNING`), also under concurrent returns.
- Customers: `GET /api/admin/customers` is a page (sorts `name`, `orders`, `spent`, `lastOrder`, `createdAt`; `q` = name, email or phone digits; no cursor and no `limit`), `GET /:id` (orders with payment status, current consent per purpose and the consent history), `PATCH /:id` (name, email, notes, phone: normalized to E.164, `409 duplicate_phone` when another customer has it), audited. Lifetime totals count booked orders (confirmed, fulfilled, delivered): `lifetimeValue` is what they owe net of returns, `netPaid` payments minus refunds, `balance` the difference, first and last order by `created_at`. Merging customers is not built.
- Search: `GET /api/admin/search?q=` answers the groups `orders`, `products`, `customers`, `suppliers`, `purchases`, `brands`, `categories`, `concerns`, `routines`, `collections` and `promotions`, each `{ id, label, hint }[]` with at most 5 hits. Orders and products query their own searchable columns; the other nine groups call the list function of their module, so a record is found by what its screen would find it by.
- Inventory (`/api/admin/inventory`): `GET /` is a page of the stock per size (sorts `product`, `sku`, `onHand`, `stockValue`, `expiringUnits`, `expiredUnits`, `reorderPoint`; `view` = `low`, `out`, `expiring` or `expired`; `q` = product, brand, SKU or barcode); on hand counts only units of lots that have not expired, and expired units are listed apart (`expiredUnits`, `expiredValue`) until written off. `GET /summary` is the totals (units, value, expiring, expired, `belowReorderPoint`). `GET /lots` is a page of the lots that still hold units, expired ones too (sorts `expiresOn`, `product`, `sku`, `code`, `available`, `unitCost`, `value`; `view` = `expiring` or `expired`; `q` also matches the lot code). `GET /movements` is the stock ledger as a feed, `{ items, nextCursor }`, newest first (`kind`, `reason`, `sku`, `lotId`, `from`/`to`; `cursor`, `limit` up to 200) with the order each row belongs to and its value at lot cost; the filters are `movementFilters` (`src/lib/schemas/inventory.ts`), shared with `movements.csv`, and the size is filtered by `sku` (it was `variantId`). `POST /adjustments` writes an adjustment (a stock count is one) or a waste on a lot. The stock and lot pages sum the whole ledger on every request.
- `GET /api/admin/audit-events` answers `{ items, nextCursor }` (newest first; `entityType` + `entityId`, `actor` user id, `verb` (`create`, `update`, `status` or `archive`), `action` exact or a prefix ending in `.` such as `order.`, `from`/`to` local days; pass `nextCursor` back as `cursor`, `limit` up to 200). `GET /api/admin/audit-events/actors` lists the admins who have acted, for the actor filter. `src/lib/schemas/audit.ts` lists the entity types and verbs the log can be filtered by, and `audit.test.ts` scans the server source and fails when the API writes one that is not listed.
- CSV (`GET /api/admin/exports/...`): `orders.csv` and `order-lines.csv` (the order list filters), `customers.csv` (`q`), `movements.csv` (ledger filters), `reports/{sales,products,brands,losses,stock,reorder}.csv` (the report parameters; `totals=true` adds a last `total` row to sales, products and brands, whose money comes from the exact sum, lot costs rounded once, so it can differ by a cent from the sum of the rounded rows). RFC 4180 with CRLF, UTF-8 with a BOM for Excel, money as decimals of the currency's minor unit (`1234.50`), instants as the store's local date and time (`2026-10-05 18:26:49`), text starting with `=`, `+`, `-`, `@`, tab or CR prefixed with `'` (formula injection; this includes phones such as `'+50371234567`). The CSVs read the list by cursor, page by page (not through the screens' offset pages); the first page is read before the response starts, so a failure is still an error answer. At most 10 exports per admin per minute (`EXPORT_LIMITER`, `429 rate_limited`).

### Reports

`GET /api/admin/reports/...` and the dashboard compute every figure with the same functions (`src/server/domain/sales.ts`, `reports.ts`, `reorder.ts`, read by `report-data.ts`), on whole local days of the store (`from`, `to` as `YYYY-MM-DD`, both included, at most 1,096 days; bounds by `startOfLocalDay`, DST-safe). Reports filter on indexed dates (`orders.fulfilled_at`, `orders.confirmed_at`, `inventory_movements.created_at`, `returns.created_at`, `payments(kind, recorded_at)`; audit events by `(actor_user_id, id)`). Money is in minor units; lot costs are summed in `_e4` units and rounded once per reported figure, so a total can differ from the sum of its rounded rows by a cent.

- Sale: an order that left the store (`fulfilled` or `delivered`), dated by the local day of `fulfilled_at`, net of every return of its units whenever the return happened. Cancelled orders are not sales (a fulfilled order cancelled after a failed delivery brought every unit back). Pending and confirmed orders are not sales yet.
  - `revenue` = what the order owes (`amountOwed`): merchandise + `shipping`.
  - `merchandise` = kept units x order price - the discount kept (in proportion to the kept value), spread over the lines by kept value with the largest remainder so lines add up to the order.
  - `shipping` = the fee, while at least one unit is kept.
  - `costOfGoodsSold` = landed cost (`lots.unit_cost_e4`) of the units that left their lots for the sale minus the cost of the units that came back (restocked or written off).
  - `grossProfit` = merchandise - cost of goods sold; `margin` = gross profit / merchandise (4 decimals, null without merchandise). Shipping fees are not product margin, and written-off returns are a loss of the day they were recorded (losses report), not of the sale.
  - `units` = kept units; products and brands also give `unitsSold` and `unitsReturned`.
- `sales?from&to&granularity=day|week|month`: totals and one row per period, empty periods included; weeks start on Monday, months on the 1st; `partial` marks a first or last period cut by the range.
- `products?from&to`, `brands?from&to`: the sale figures per variant (named as last sold, from the order line snapshot) and per brand as written on the order lines, by merchandise.
- `losses?from&to`, by the local day each record was made, whatever the order's status: `returns` (count, units, value at order price before discount, by reason; lot cost restocked and written off), `refunds` (confirmed refunds by `recorded_at`), `writeOffs` (all `waste` movements by reason at lot cost: expired, damaged, testers, returns that could not be resold...), `adjustments` (net units and value of `adjustment` movements; negative is shrinkage) and `totalLoss` = write-offs - adjustments value.
- `stock?expiryWindowDays` (default `expiry_warning_days`), as of the store's today: per variant (active, or with stock) and in total, `onHand` and `value` = units of lots that have not expired at lot cost; `atRiskUnits`/`atRiskValue` = the part of it in lots expiring within the window (a lot sells through its expiry date); `expiredUnits`/`expiredValue` = units still in expired lots (to write off, not an asset); `belowReorderPoint` when on hand <= `variants.reorder_point`; `expiringLots` lists the lots at risk.
- `reorder?lookbackWeeks=8&targetWeeks[&leadTimeDays]` (lookback 1-52 weeks, default 8; target 1-52 weeks required), per active variant of a product that is not archived, most urgent first:
  - Supplier (`supplier`, with `source`): the variant's preferred active supplier item of an active supplier, else its only one; none when it has several and none is preferred. `leadTimeDays` is the query's `leadTimeDays` when given (an override for every variant, `leadTimeSource: "query"`), else the supplier's (`"supplier"`); when neither is known it is null, counted as 0 and flagged `lead_time_unknown`.
  - `unitsSold` = kept units of sales in the last `lookbackWeeks x 7` local days (`weeklyUnits`, oldest week first, weeks ending today); `daysObserved` = those days, or the days since the first lot was received when that is later, but never fewer than 14 days (or the whole lookback when shorter): a shorter history is spread over that window and flagged `short_history`, so a first day's sales are not extrapolated; `ratePerDay` = units sold / days observed.
  - `onHand` = units of lots not expired; `committed` = units held by open orders (confirmed, and pending within their confirmation deadline, the storefront's rule); `backorders` = committed beyond on hand (since nothing is sold without units, only waste, a count or an expiry after the promise leaves any); `projectedExpiringUnits` = units that will expire before they sell (committed units leave first, then the rate takes lots first-expired-first-out); `usable` = on hand - committed - projected expiring; `daysOfCover` = usable / rate; `stockoutOn` = today + whole days of cover.
  - `reorderPoint` = `variants.reorder_point` when set (the owner's minimum), else ceil(rate x lead time), the demand while an order is on its way; `orderUpTo` = reorder point + ceil(rate x 7 x target weeks); `gap` = order up to - usable.
  - `shelfLifeCap`: a new lot arrives after the lead time with at least `min_shelf_life_days` of life (shorter lots are swapped at receiving) and starts selling when the usable stock is gone, so at most floor(rate x (lead time + min shelf life - max(lead time, usable / rate))) units of it sell before it expires, plus the backorders it fills. Not applied when `min_shelf_life_days` is empty (`min_shelf_life_not_set`).
  - `topUpQuantity` = min(gap, cap); without sales, the gap to the owner's reorder point, else the backorders. `orderQuantity` = the suggestion raised to the supplier item's minimum order and rounded up to whole packs (`rounded_to_pack_or_minimum`; `rounded_above_shelf_life_cap` when that passes the cap). `suggestedQuantity` = the top-up when usable <= reorder point (with no sales and no owner's point, only below 0), when orders wait for stock, or when the stock runs out within the lead time; else 0.
  - `unitCost` = landed cost of the latest lot bought at a price (free units excluded); `unitMargin` = current price - unit cost; `urgency` = 1 when usable stock is gone, else min(1, (lead time + 7) / days of cover); `priorityScore` = urgency x (units per week + backorders) x unit margin, in minor units (gross profit per week at stake), 0 when nothing is suggested and null when the margin is unknown. `reasons`: `backordered`, `below_reorder_point`, `stockout_within_lead_time`, `stock_expiring_unsold`, `capped_by_shelf_life`, `min_shelf_life_not_set`, `no_sales_in_lookback`, `no_cost`, `no_price`, `lead_time_unknown`, `short_history`, `rounded_to_pack_or_minimum`, `rounded_above_shelf_life_cap`.
- Dashboard (`GET /api/admin/dashboard?days=30`, the last `days` local days, today included): `sales` = the sales totals of the range (same as `reports/sales`), `byDay` its revenue, orders and gross profit per day, `topProducts` the first five of `reports/products`; `bookings` = orders confirmed in the range (`confirmed_at`) that are not cancelled, valued at what they owe now; `losses` = the losses report of the range (write-offs count from the ledger, so a write-off of an order cancelled later still counts); `pendingOrders`, and `overduePendingOrders` = pending orders placed before yesterday (consumer law: confirm by the next calendar day); `stock` = the stock report totals with `belowReorderPoint` (the variants the reorder report covers: active, of a product that is not archived) and `expiring` its lots at risk.

### Security

- `hono/csrf` on the whole API: form-like or body-less requests must come from the same origin (`Origin` or `Sec-Fetch-Site`); JSON requests from another origin need a CORS preflight the API never grants. Better Auth (`/api/auth/*`) checks the origin itself (a cross-origin sign-out with a session is `403 INVALID_ORIGIN`).
- Every response (pages and API) carries `Content-Security-Policy-Report-Only` (self only, inline scripts and styles allowed for TanStack Start hydration, `frame-ancestors 'none'`), `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY` and a `Permissions-Policy`; `/api/admin` and `/api/auth` answers are `Cache-Control: no-store` (`src/server/security.ts`). No reporting endpoint is configured, so violations only show in the browser console: enforce the CSP after a pass through the live site with the console open.
- Request bodies: 16 KB on `/api/orders/*` and on Better Auth's `/api/auth/*` (`src/server/auth-api.ts`, with or without a content length), 128 KB elsewhere (`413 payload_too_large`).
- New public orders are rate limited per client IP (`cf-connecting-ip`) with the Workers Rate Limiting binding `ORDER_LIMITER` (10 per minute, `wrangler.jsonc`; `429 rate_limited`); retries of an existing order are answered before the limit. Order lookups and code checks (`/orders/lookup`, `/promotions/validate`) use the same binding with their own counter per client (discount codes and order codes can be guessed), and the same 16 KB body limit. A public order without `cf-connecting-ip` (which Cloudflare and the local runtime always set) is refused with `400 client_ip_missing` (`src/server/client-ip.ts`), never counted under a shared key. CSV exports are limited per admin with `EXPORT_LIMITER` (10 per minute). The binding works in local dev; on Cloudflare it is available on the Free plan per its docs, not verified against a deployed Worker here.
- Better Auth reads the client IP from `cf-connecting-ip`, so sign-in limits count real clients.
- `workers_dev` and `preview_urls` are off: the Worker answers only on its custom domain, `eclalune.com` (`routes` with `custom_domain: true`). `wrangler.jsonc` has no comments, so scripts can read it as JSON; the reasons for its settings live here.

### Search engines

- The store layout (`src/routes/_store/route.tsx`, `storeHead` in `src/lib/seo.ts`) gives every store page its title and description, `rel=canonical` to its own URL in its own locale without search parameters (a filtered listing points at the listing), `hreflang` alternates `es` (no prefix), `en` (`/en/...`) and `x-default` (the Spanish URL), Open Graph (`og:locale` is `<language>_<country_code>`; default image `/og-default.png` or `/og-default-en.png`, 1200 x 630) and `twitter:card`. URLs are built with Paraglide's `localizeUrl`, so they match the router's: the English home is `/en/` (`/en` redirects there).
- Pages override title, description and `og:title` with `pageMeta`. A product page also sets `og:type` `product`, its largest photo of at least 200 x 200 as preview, and `Product` (offer price as a decimal, `availability` `InStock` with sellable units, else `OutOfStock`) and `BreadcrumbList` JSON-LD. The home pages carry `OnlineStore` (name, legal name, email, phone and the WhatsApp contact point from the store settings, logo `/logo.png`, the store country as area served) and `WebSite` (its `name`, the store name, is the site name Google shows).
- Absolute URLs use `siteOrigin()` (`src/lib/site-origin.ts`): `BETTER_AUTH_URL` on the server, so the Host of a request never changes a canonical URL, and the page's origin in the browser. In production it must be `https://eclalune.com`.
- An unknown address (catch-all `src/routes/_store/$.tsx`), an unknown product, page, need or type answers HTTP 404 with the store's 404 page inside the header and footer, the title "Página no encontrada" and `robots noindex` (the `/_store` head checks `match.status`).
- A route with `staticData: { noindex: true }` (back office, admin sign-in, cart) gets `robots noindex` from the root route, also in the HTML of pages rendered only in the browser, and no canonical, alternates or structured data.
- The Worker answers `/robots.txt`, `/sitemap.xml` and `/llms.txt` before the app (`src/server/seo-files.ts`; builders in `src/server/domain/seo-files.ts`), with `Cache-Control: public, max-age=3600`. robots.txt disallows `/admin`, `/en/admin` and `/api/` and names the sitemap. The cart stays crawlable on purpose: it is linked from every page, and Google only sees a `noindex` on pages it may crawl. The sitemap lists the home page, the product and routine listings, `/company`, the need, type and brand pages with published products, each routine shown, each published product (`lastmod` from `products.updated_at`) and each published page (`/pages/<slug>`), once per locale with every alternate (`sitemapEntries`).
- Icons, `site.webmanifest`, the logo PNG and the preview images are in `public/`, generated by `scripts/brand_assets.py` (see docs/BRAND_GUIDELINES.md). What to do in Google Search Console and Bing after a deploy: [docs/deployment/SEARCH_CONSOLE.md](../docs/deployment/SEARCH_CONSOLE.md).

### Migrations

- The baseline is two migrations, squashed on October 24, 2026 while the store had no orders to keep: `drizzle/0000_baseline.sql` is every table, generated by drizzle-kit from `src/db/schema/` and `src/db/auth-schema.ts`, and `drizzle/0001_integrity_triggers.sql` is every trigger and the one expression index, a custom migration (`bunx drizzle-kit generate --custom`) written for the D1 statement splitter: uppercase `BEGIN`/`END`, no `CASE` in trigger bodies, LF endings. The production database was reset to this baseline in place on October 25, 2026 (`docs/NEXT_SESSION.md`, "Production database"). `drizzle/0002_landing_texts.sql` is the first additive one (need and type page texts, a routine's need, the founding year), not yet applied in production; `seed/sync-texts.ts` fills its columns on a database that already has data.
- D1 binds JavaScript numbers as REAL: arithmetic on a bound number in SQL is a float operation (`cast(? as integer)` keeps an integer division), and batched selects need unique column names (D1 returns batch rows as objects keyed by name, so drizzle misplaces a repeated one: alias it with `.as()`).
- `src/db/migrations.test.ts` applies every migration to SQLite (foreign keys on) and fails when a trigger that a migration created is missing, when generated SQL rebuilds or drops a table, or when a trigger stops refusing what it should.
- After the first production migration, changes are additive only: new tables, indexes and triggers, `ALTER TABLE ADD COLUMN` that is nullable or has a constant default (a default such as `now` fails on D1, drizzle issue #6408), `UNIQUE` as a separate `CREATE UNIQUE INDEX`. Read every generated SQL file: no `__new_` rebuilds, `DROP TABLE` or `PRAGMA foreign_keys`. D1 ignores the pragma, and a drizzle-kit rebuild fails anyway: it copies the table-qualified CHECKs (`"orders"."status" in (...)`) into `__new_orders`, which SQLite rejects; a parent table's rebuild also stops at its no-delete trigger. A hand-written rebuild (only ever for a leaf table) must re-create that table's CHECKs unqualified and every trigger on it, since `DROP TABLE` drops them silently; the migrations test catches a missing one. Rules that may evolve are triggers (`DROP TRIGGER` + `CREATE TRIGGER`), not CHECKs.

## Back office

The back office (`/admin`, rendered in the browser only; every call is checked again on the server) is thin routes over feature folders and a few shared kits. Look and layout rules: [docs/strategy/DESIGN_SYSTEM.md](../docs/strategy/DESIGN_SYSTEM.md), section 4.

### Structure

- **Routes** (`src/routes/admin/<module>/`): `route.tsx` (the breadcrumb and an `Outlet`), `index.tsx` (the list), `new.tsx` and `$id.tsx` where the module has them. A route reads the URL, starts the queries and renders a feature, nothing more. Brands, categories and needs are one file each (create and edit are a dialog). Inventory is four routes (`/admin/inventory`, `/lots`, `/movements`, `/reorder`), settings five under link tabs (`/admin/settings/store`, `/payments`, `/promises`, `/pages`, `/invoicing`, each card its own form), reports six (`/admin/reports`, `/products`, `/brands`, `/losses`, `/stock`, `/reorder`, with the range in the URL and a CSV link on each). The overview is `/admin`.
- **Features** (`src/features/<module>/`): the screens (tables, columns, dialogs, editors), `queries.ts` (query options; keys start with `["admin", <module>]`), `mutations.ts` and `search.ts` (the defaults of the list and the link of its CSV).
- **Schemas** (`src/lib/schemas/<module>.ts`): the query of a list (page, sort, filters), its sort whitelist and the limits both sides check are one zod schema, imported by the Hono route (`validate("query", ...)`) and by the screen (`validateSearch`), so the address of a screen is the query the server validates. The body of a form has its schema next to the form.
- **Errors:** `src/lib/errors.ts` maps an API error code to a Paraglide message; `errors.test.ts` scans the server source for every `error: "code"` and fails when a code has no message, except the ones it lists as shown generically.

### Lists

- **Query:** `pagedSearch(sorts, defaults)` (`src/lib/list.ts`) gives `page`, `pageSize` (10, 25, 50 or 100; 25 by default), `sort` (one of the list's whitelist), `dir` and `q`; a list adds its filters with `.extend`.
- **Answer:** `Paged<T>` = `{ items, total, page, pageSize, pageCount }` (`toPaged`, `pageWindow` and `sortBy` in `src/server/domain/list-query.ts`). A page past the end is empty with the real total; `sortBy` orders by the chosen column and then by id in the same direction, so equal rows keep one order from page to page. Ledgers that only grow (stock movements, audit events, page versions, media files) are `Feed<T>` = `{ items, nextCursor }` with an id cursor instead.
- **One round trip:** the page and its `count()` run in one `db.batch`. D1 returns batch rows as objects keyed by column name, so columns that share a name (the ids of joined tables) are aliased with `.as()`.
- **State in the URL:** a list route has `validateSearch` (the same schema), `stripSearchParams(defaults)` (a default stays out of the address) and a loader that starts `prefetchQuery` without awaiting it, so the page renders at once, the table shows its own skeleton, and paging or filtering keeps the previous rows (dimmed) while the next page loads.
- **Table kit** (`src/components/admin/data-table/`): `DataTable` over TanStack Table 9 in manual mode (`useDataTable`: pagination and sorting are the server's, the table state is the URL's), `TableToolbar`, `TableSearch` (writes to the URL 300 ms after the last key), `SelectFilter`, `DateRangeFilter` (days of the store), `StatusTabs`, `TablePagination` and `RowActions`. It draws the skeleton rows, the error with a retry, "no results" with a way to clear the filters, and an `empty` slot for a list with nothing in it.

### Forms

- **Kit** (`src/components/admin/form/`): `useAppForm` (TanStack Form's `createFormHook`) with the fields `TextField`, `TextareaField`, `MoneyField`, `SelectField`, `CheckboxField`, `SwitchField`, `DateField`, `ComboboxField` (a search over a long list, on `command` and `popover`) and `MediaField` (`media-picker.tsx`: pick an uploaded image or upload one), plus `SubmitButton` and `FormError`. `LocaleTabs` repeats the same fields once per language, the default one first, and marks a tab whose fields have errors.
- **Validation:** every form passes `validationLogic` (`revalidateLogic()`: nothing is said until the first submit, then each change revalidates the whole form), its zod schema as `validators.onDynamic` and the API call in `validators.onSubmitAsync`. A refusal from the API comes back through `serverErrors`: `invalid_request` lists the paths that failed, each goes to its field, and the rest to `FormError`. Why `revalidateLogic`: a schema on `onSubmit` and `onChange` left its errors on fields the user had not touched, and the form then refused to submit without saying why.

### Shell and charts

- **Shell** (`src/components/admin/`): `AdminShell` (the shadcn sidebar, collapsible to icons on wide screens and a sheet on phones, its state kept in a cookie), `AppSidebar` (the sections, in `nav.ts`), `NavUser` (language, the store, sign out) and `AdminHeader`. Breadcrumbs come from the matched routes: `staticData.crumb` (a Paraglide message) or, for a route named by its data (an order's code, a product's name), the `{ crumb }` its loader returns (`LoaderCrumb`, `src/lib/route-data.ts`). Ctrl+K (Cmd+K on a Mac) opens `CommandSearch` (`cmdk`): the sections, and from two letters on the records of `GET /api/admin/search`.
- **Pages:** `PageHeader` (the title bar of a list or a record, with `HeaderActions`), `PageTabs`, `DetailPage` and `DetailColumns` (a record's page and its two columns), `QueryState`, `QueryError`, the skeletons (`DetailSkeleton`, `RecordNotFound`), `Panel` (a flat bordered card) with `Section` (the card with a header row; `Fact` is a label over its value) and `FormCard` (a card that is one form with its own save) built on it, `StatCard` with `StatGrid`, and `ChartCard`. Spacing comes from the `--spacing-admin-*` tokens of `styles.css`, which `cn` knows (`src/lib/cn.ts`), so a component's `p-admin-card` and a caller's `p-0` replace each other.
- **Charts:** `ChartCard` draws the shadcn `chart` (Recharts) from `series-chart.tsx`, loaded with `lazy()`: that chunk (about 340 kB, 101 kB gzip) is fetched when a chart is first shown and is not in the entry chunk (about 445 kB, 139 kB gzip; both measured with `bun run build` on October 25, 2026).
- **Audit labels** live in `src/features/audit/labels.ts`; the entity types and verbs they cover are `src/lib/schemas/audit.ts` (see the audit log above).

## Admin access

- Public sign-up is disabled. Accounts are created with `bun run admin:create -- --email you@example.com --name "Your Name"` (add `--remote` for production). The password comes from `ADMIN_PASSWORD` or is generated and printed once.
- `/admin` redirects to `/admin/login` without a session. Every `/api/admin/*` call is checked on the server (`requireAdmin`, `src/server/auth.ts`): no session is 401, a session that is not `isAdmin` (`src/lib/roles.ts`: the `admin` role among the user's comma-separated roles, and not banned) is 403. The admin layout uses the same `isAdmin` to decide what to show. `src/server/auth.test.ts` requests every route of the admin router without a session and fails if one does not answer 401.
- Google Workspace sign-in (recommended: no password hashing in the Worker) turns on when `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `GOOGLE_WORKSPACE_DOMAIN` are set. Only existing admins can sign in; the Google account must belong to that Workspace domain (`hd` claim). Create a Google-only admin with `--google-only`. The OAuth client lives in the Google Cloud project `eclalune-store` (organization eclalune.com, audience Internal). Redirect URI: `<BETTER_AUTH_URL>/api/auth/callback/google`. Once Google is configured, password sign-in is off: `GET /api/sign-in-methods` answers `{ google, password }`, the login screen shows only the methods that are on, and Better Auth answers `EMAIL_PASSWORD_DISABLED` to a password attempt (a scrypt hash is heavy for a Worker). Create the admins of that deployment with `--google-only`. Google is not a trusted provider for account linking: the account links to the existing admin only when Google reports the email as verified and the admin's email is verified (`create-admin` sets it). Google's tokens are stored encrypted (`encryptOAuthTokens`).
- Sign-in is limited to 5 attempts per minute per client IP (`cf-connecting-ip`), stored in D1; `get-session`, read-only and called on every admin page, is not counted. Sessions last 7 days. The admin plugin endpoints the back office has no screen for (create or update a user, set a role or a password, remove a user, impersonate) are in `disabledPaths` and answer 404; `src/lib/auth.test.ts` checks this against the real configuration. The Worker refuses to start when `BETTER_AUTH_URL` is not https and not localhost.
- Auth options live in `src/server/auth/options.ts`; what the Worker decides from its environment (Google, https) is in `src/server/auth/config.ts`. After changing options, run `bun run auth:generate` (the `auth` CLI, `bunx auth@latest`), then `bun run db:generate` and `bun run db:migrate`. The db scripts and `create-admin` target the `DB` binding of `wrangler.jsonc`, so a different database only needs that file changed; `create-admin` also checks the password length (12 to 128).
- Secrets: `BETTER_AUTH_SECRET` and `BETTER_AUTH_URL` go in `.dev.vars` locally (gitignored) and in `wrangler secret put` for production. Generate a secret with `bunx auth@latest secret`.

Set the seven secrets listed in `wrangler.jsonc` (`secrets.required`; `wrangler deploy` refuses to run while one is missing): `BETTER_AUTH_SECRET` (a new value, not the local one), `BETTER_AUTH_URL` (`https://eclalune.com`), the three `GOOGLE_*` values and `GREENERSYS_API_URL` / `GREENERSYS_API_KEY` (the production tenant and its key; empty leaves invoicing off), with `bunx wrangler secret put <NAME>`. On the first deploy the Worker does not exist yet, so pass them with `wrangler deploy --secrets-file`. The private bucket `eclalune-documents` (binding `DOCUMENTS`, signed invoices) must exist before a deploy: `bunx wrangler r2 bucket create eclalune-documents`. Then `bun run admin:create -- --email ... --name ... --remote`. Locally, `.dev.vars` needs the same seven names (Google values may be empty; the GreenerSys pair holds the **test** tenant and key, never production ones).
6. `bun run fonts` (the font files are gitignored, so a deploy from a clean checkout would serve 404s), then `bun run deploy`. The deploy keeps `eclalune.com` and `www.eclalune.com` attached as the Worker's custom domains (`routes` in `wrangler.jsonc`).
7. Password sign-in needs the Workers Paid plan (Google sign-in does not). Better Auth (>= 1.6) hashes passwords with native `node:crypto` scrypt on Workers, but any OWASP-strength hash takes far more than the Free plan's 10 ms of CPU per request (error 1102). Measured locally: scrypt about 200-300 ms, PBKDF2-SHA256 600k about 300 ms, argon2id (WASM) about 600 ms. Do not weaken the hash to fit Free. The only password-free option on Free is a magic link or email OTP for admins. Sources: https://developers.cloudflare.com/workers/platform/limits/, https://github.com/better-auth/better-auth/pull/8685
8. In `/admin/settings`, fill in the WhatsApp number and the legal identity (legal name, tax ID and its label, address): checkout stays closed until they are set. Check the time zone, country, order prefix and published promises, and add shipping zones once their fees are known.
